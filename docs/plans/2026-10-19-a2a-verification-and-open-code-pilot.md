# 主动求助验证与 LiveCodeBench 小题集：执行结果

日期：2026-10-19。已完成真实求助验证及题集构建；新的编码能力对比尚未启动。

## 1. 这次先检查“电话会不会打、需不需要打”

任务是核验明日能否完成 84 件工单：3 人，每人工作 7 小时。处理速率和随机签名回执只放在搭档的本轮资料卡中，最初不提供给请求者。请求者如果要交出正确结果，必须取得这条记录，而不是猜一个数字。

搭档回复处理速率为每人每小时 5 件及随机回执后，请求者应提交：容量 105、能够完成、相同回执。回执每次独立生成，因此“算对 105”本身不算验证通过；还要验证请求、受邀者发言、回复关联和恢复输入。

| 情境 | Flash 主导 | GPT 主导 | 实际行为 |
| --- | --- | --- | --- |
| 明确要求先找搭档核验 | 通过 | 通过 | 各一次真实 wait_reply，回复后恢复并交付 |
| 不要求必须求助，只说明搭档持有缺失记录 | 通过 | 通过 | 两者都自主调用求助，取得并使用随机回执 |
| 直接给齐全部记录 | 通过 | 通过 | 两者直接提交，各一次调用，没有邀请 |

最有意义的是中间一行：请求者原始输入中没有回执，也没有“第一轮必须调用”的指令，搭档没有预排发言，两个模型都主动发起了实际工具调用。

真实模型：Codex CLI GPT-6.1 Sol / Antigravity CLI Gemini 3.8 Flash，均 low。共 6 个探针、14 个宿主调用、4 次实际等待往返；全部通过。14/14 有用量，未发现禁止的原生工具活动。执行文件指纹复核无变化。

这支持的结论是：**在这个小型受控信息缺口场景中，两款配置能自主求助并使用回复；信息齐全时能直接交付。** 每种情境、方向只有一次样本，尚不能说明复杂任务中委派时机稳定，也不能证明求助提高编码能力。

新增费用按旧 pilot 冻结的标准 API 基础费率、不计缓存折扣，估算 $0.8926785；不是 CLI 实际账单。旧批次累计已知保守估算为 $2.3662925，两者相加约 $3.258971，仍另有一次历史容量失败用量未知。此次调用间软停止阈值为 $1.50，不是正在执行请求的硬封顶。

真实证据位于 `output/eval/a2a-probes-20261019-r1/`：`manifest.json`、`calls.jsonl`、每个探针的独立数据库、实际工具列表、可见提示及 CLI 诊断。对外报告只使用正式发言与事件，不依赖思考日志判断求助。

## 2. 为这次验证修复了什么

- MCP schema 现已同时声明 `fire_and_forget` 和 `wait_reply`，与执行器一致。
- 回复事件正确关联实际消息的 `id`，兼容旧模拟事件中的 `message_id`。
- 为探针提供只预排请求者的计划入口，受邀者通过实际 A2A 队列执行；没有用固定发言冒充接力。
- 探针额外守住每次往返 3 个宿主调用、全批最多 14 个的边界，恢复回合也计入；通用旧 D 的预算语义没有因此自动完成重构。
- 实际 `tools/list` 返回被持久化，能够复查模型看到了哪些工具与模式。

默认离线计划，不调用模型：

```bash
.venv/bin/python scripts/run_a2a_probes.py
```

显式 `--run` 才启动真实 CLI；重跑须新输出目录，费用重新记账。协议探针失败会先停止，不拿缺失的链路继续做能力结论。

## 3. 再准备真正需要写程序的问题

采用 [LiveCodeBench 官方数据](https://huggingface.co/datasets/livecodebench/code_generation_lite)的 `v6` 增量快照。本机直连下载失败后，使用镜像取得源文件，并与[官方文件页的 SHA-256](https://huggingface.co/datasets/livecodebench/code_generation_lite/blob/main/test6.jsonl)逐字核对。没有执行远程数据加载脚本。

| 分区 | 题目 | 上游难度 | 要观察的错误 |
| --- | --- | --- | --- |
| 开发 | abc387_c Snake Numbers | medium | 数字计数和区间边界 |
| 开发 | abc391_e Hierarchical Majority Vote | hard | 丢失递归结构，只看整体多数 |
| 锁定 | abc400_b Sum of Geometric Series | easy | 阈值边界；简单任务是否无谓协作 |
| 锁定 | abc394_d Colorful Bracket Sequence | medium | 只数括号，不检查类型和嵌套 |
| 锁定 | abc396_d Minimum XOR Path | medium | 对 XOR 使用不适用的贪心，或违反简单路径要求 |
| 锁定 | abc395_e Flip Edge | hard | 遗漏翻转状态、混淆操作代价或整数范围 |

题目 ID 在模型编码实验前已固定，不按团队胜负挑题。上表的错误描述和算法标签仅供分析，模型输入不包含这些提示。所有策略都拿到相同原题、公开样例和交付要求。

每题保留 40 个原始私有测试。独立参考实现通过全部 19 个公开样例和 240 个私有测试，共 259/259；一个开发题错误解能过 2/2 公开样例，却只有 16/40 私有测试通过。现在可以识别“看起来跑通样例，但算法仍然错误”的交付。

评分使用隔离的 Python stdin/stdout 执行，逐例比较实际输出；不使用关键词评分或模型评委。模型侧不接触私有测试和参考实现，也不根据私有反馈反复修订。

生成的题集：`output/eval/open-code-v1/`。可复跑选择清单、构建命令、评分命令和限制见[题集说明](../../eval/pilots/open-code-v1/README.md)。
