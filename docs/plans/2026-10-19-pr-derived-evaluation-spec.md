## 2. 一道题如何从 PR 中产生

1. **确认来源**：参考实现已合并；修复前 base 使用该合并/压缩合并的第一父提交，并核对 SHA。
2. **限定子问题**：一个 PR 常含多件事，先选择能独立描述和验收的行为。不能把 #13 的超时、认证、文件交接和界面记录混成一句模糊任务。
3. **改写需求**：只写故障现象、复现条件、预期行为、必要接口和边界；剔除 PR 原文中的根因、解法、补丁和测试结果。
4. **构建独立验收**：目标检查在 base 失败、参考后通过；保留行为在前后均通过。验证失败必须是任务行为失败，不能是缺依赖、fixture 错误或测试根本没收集到。
5. **分开资料**：模型只看基础仓库与改写任务。参考提交、来源 PR、验收代码和后续修复历史仅供 evaluator 使用。
6. **保存证据**：固定来源、测试/补丁哈希、实际依赖版本和原始结果，允许另一份满足需求的实现通过。

当前构建器和检查在 [PR 题集目录](../../eval/pilots/pr-replay-v1/README.md)，准备入口为 `scripts/prepare_pr_pilot.py`。默认只准备，显式 `--qualify` 才在本地副本运行验收；所有模式均不调用模型。

## 4. 如何避免“考生已经拿到答案”

模型工作目录从指定旧版本归档，再初始化为只有一个提交、没有远端的新 Git 仓库。不能把原项目的完整 `.git` 或普通 linked worktree 直接交给求解者，否则可能经后续提交看到答案。当前旧 base 不含新增评测目录；以后从新基线构题还需排除题库与参考解。

公共题面使用 repo-001/repo-002 等 ID，不给 PR 编号、PR 链接或修复 SHA。归档及 Git 隔离仍不是完整安全边界；真实执行前要限制访问 evaluator private 目录和通过网络读取公开 PR。模型不继承本次设计对话或其他任务的求解记录。

评分阶段用独立副本应用最终补丁，再注入可信验收。不能让模型通过删除测试、修改 pytest 配置或直接写验收结果“过关”。修改策略和完整隔离尚需接入真实执行器，当前只回放受信任参考补丁。

## 5. 为什么不把这两题叫锁定集

这些 PR 已经被阅读和讨论，且有 AI 参与历史实现；更适合开发回放和探索，不能直接声称盲测或训练未见。

按原始需求、根因、后续修复链和堆叠依赖划分家族，而不是按 PR 编号随机分。例如圆桌的 #7/#8/#9 存在明显演进关系，需要共同审查分区；一个 PR 拆出的多个子题也不能分别充当开发题和独立锁定题。

可以先用历史 PR 建立回放型探索集。更强的锁定证据来自未来的新任务：在修复和验收成绩暴露给求解流程前冻结需求、基础版本、环境和独立验收。当前锁定题数量为 0，不用未回放的候选凑满“四题”。

## 6. 对协作实验的意义及下一步

这类题更接近产品的软件维护路径：读仓库、定位问题、改代码、运行检查、保留正常行为并交付补丁。它也给协作留下自然机会，例如请求独立复核接口边界或验证跨模块影响；仍不能假定多文件任务一定需要多 Agent。

继续保留 A-Flash、A-GPT、B-Flash、B-GPT、固定 C 和按需 D。所有组拥有相同材料、仓库工具和费用/时间上限；禁用模型 fallback，D 允许直接完成。将最终验收、回归、耗时和费用与实际模型求助 trace 对齐；没有同构或等计算量消融时，不单独归因于模型多样性或 A2A 机制。

被测软件本身的 MCP/A2A 测试事件与求解过程的模型协作事件必须分开保存，不能把运行单元测试时的假 Agent 接力当成真实协作。这次 `model_calls=0`，新增模型费用为 0。

下一步应先把一题的隔离仓库读写、公开测试、最终补丁捕获和私有验收接入真实 Runner，完成 A 与 D 的接入冒烟，再用实际用量确定批次预算。旧闭卷答题环境和旧四步 D 不直接适用。当前记录的宿主虚拟环境尚不是固定容器镜像，也不等同于完整 SWE-bench 标准环境。
