## 1. 需要分别验证的四件事

“不同模型组成团队效果好”可能来自更强的成员、更多计算、独立答案互补或交流本身。设计应分别回答：

1. 团队能否超过开发集选出的最佳单模型，而不仅超过最弱成员？
2. 相同工作流下，异构模 型组合是否超过同构模型组合？
3. 允许相互交流是否超过独立作答后统一汇总？
4. 动态 A2A 是否超过固定协作，收益是否只是来自额外回合？

题目不应规定“某品牌模型擅长规划、某品牌擅长代码”。能力差异要从独立成绩中测出，不能写进结论前提。

## 2. 固定模型池，但不把 CLI 名称当模型名称

先选择三个明确模型快照 M1 / M2 / M3；同品牌不同版本也可以作为不同成员，但必须完整记录。不能仅用 `codex / claude / antigravity` 作为模型身份。

每个成员记录：实际模型标识与版本、推理配置、Provider、CLI 版本、工具权限、原生 delegation 能力、上下文能力、用量采集能力、计费来源与日期。CLI 未披露真实模型时，只能命名为“某 CLI 配置”，不能据此宣称模型层面的因果结论。

区分两条跑道，报告不混合：

- **模型机制跑道**：使用公共工具、输入格式与 Agent 脚手架，尽量只改变模型；能力不兼容的任务单列。适合回答模型互补问题。
- **产品配置跑道**：保留各 CLI 的原生工具与运行特征。适合回答用户实际部署哪套组合更好；差异归于整套配置。

若 CLI 无法共享同一工具执行环境，先做产品配置跑道，不把工具强弱归因于模型能力。

主实验中性人格，真实角色人格另做消融。同一个 Agent ID 到模型的映射必须冻结；fallback 关闭，不能悄悄加入池外模型。

## 3. 实验矩阵：保留 A/B/C/D，扩展模型组成

A、B、C、D 沿用总体设计：A 一回合；B 四个同身份阶段；C 四个固定协作阶段；D 在 C 上最多加两个动态回合。

| 条件 | 模型安排 | 用途 |
| --- | --- | --- |
| A1 / A2 / A3 | 各模型独立完成 | 单模型基础能力 |
| B1 / B2 / B3 | 各模型分别自我检查、修订 | 单模型充分检查后的基线 |
| C-hom | Mi → Mi → Mi → Mi，不同 Agent 身份 | 同构固定团队 |
| D-hom | 与 C-hom 相同模型，开放 A2A | 同构动态团队 |
| C-het | Mi → Mj → Mk → Mi | 异构固定团队 |
| D-het | 与 C-het 相同配置，开放 A2A | 异构动态团队 |

MVP 每题跑这 10 个条件。Mi / Mj / Mk 的六种排列在题目间平衡；同题的 C-hom、D-hom 均使用该题的 Mi。排列在看正式成绩前分配，不根据哪种排列更好临时挑选。

这个精简矩阵估计的是“在预登记角色排列分布上的平均差异”，不表示每题测完所有同构模型与所有异构排列。要研究具体模型组合或模型×任务类型交互，需要扩展矩阵与独立任务数。

关键对照：

- C-hom − 对应 Bi：在同一个模型下，身份切换是否有价值。
- C-het − C-hom：把两个检查者换成不同模型的总体效果。
- D-het − D-hom：动态策略下的模型组成效果。
- D-het − C-het：异构组合下动态协作策略的总体效果；额外计算仍需消融。
- C/D-het − B*：是否超过开发集预选、正式阶段冻结的单模型基线。

B* 按预算档从 B1 / B2 / B3 中选择，规则在开发集确定。不能在正式集每题看完答案再选赢家，并把这种事后选择伪装成可部署的单模型策略。

若要进一步宣称“异构团队值得替代最佳同构团队”，还必须加入开发集预选的 C-hom* / D-hom*：所有成员均使用预选模型，并冻结在该预算档的配置。按题轮换的同构参照不是“最佳同构团队”，不能用其平均成绩替代这个对照。新增条件全量各重复 3 次最多增加 288 runs；与已有配置相同的运行可以在 manifest 明确的规则下复用，不重复挑样本。

### 3.1 两个解释协作收益的重要附加条件

**独立生成后汇总 E**：M1 / M2 / M3 在互不可见的会话中分别作答，由与 C-het 相同的 Mi 汇总。四回合模型组成与 C-het 相同，权限、全局预算与最终评分器一致。它回答“收益来自交流，还是收集多个独立答案就够了”。不使用隐藏评分器挑答案。

**只路由、不协作 R**：开发集上制定一个任务到模型的选择策略，正式阶段只选择一个模型运行 B。路由只能看公开任务信息，不能读取私有能力标签、答案或正式成绩。路由本身若调用模型，计入费用与时间。它回答“是否只需选对模型”。

预算有限时先跑十个核心条件；若异构团队占优，再在完整锁定集追加 E / R，以及总体设计中的 B6 / C6。未跑 E 时，不声称证明了交流机制优于独立集成。

## 4. 评测集的结构：同一题目，不同策略；模型偏好只用于分析

任务集与模型配置必须分离。题目描述只规定目标、约束、输入、工具与交付格式，不指定哪位模型必须处理哪个子任务。

保留总体设计的 60 题目标：12 个开发任务 + 48 个锁定任务；锁定集八类各 6 题。它是可启动的探索规模，不保证足以确认细分组合的微小差异。

| 类型 | 题目怎么制作 | 主要验收 | 异构协作需要解释什么 |
| --- | --- | --- | --- |
| T1 简单确定性 | JSON 抽取、规则转换、短答案 | 精确值、schema、字符限制 | 是否增加成本或把正确答案改错 |
| T2 局部修复 | 可复现 bug + 冻结依赖和仓库快照 | 隐藏测试、原测试回归 | 其他模型能否发现原模型漏掉的 bug |
| T3 组合交付 | 一个真实目标包含接口、实现、边界验证 | 子验收 + 端到端检查 | 子能力互补能否合成完整正确交付 |
| T4 强依赖推理 | 排程、事务顺序、多步骤约束 | 可执行约束验证 | 前一模型的前提是否在交接后失效 |
| T5 证据综合 | 带版本、冲突和来源的离线资料包 | 事实槽与证据定位 | 是否能纠正共同误读，而不是互相附和 |
| T6 长上下文 | 把必要条件分布在不同位置 | 条件覆盖、最终结果 | 模型差异还是上下文裁剪造成退化 |
| T7 方案权衡 | 明确资源、接口、禁用项与场景 | 硬约束 + 锚定 rubric | 是否增加有效权衡，而非篇幅 |
| T8 信息不足 | 缺参数、相互冲突且无法消解的资料 | 澄清、保留未知、固定交互脚本 | 是否把多个不确定答案汇成虚假确定 |

除了综合任务，必须保留简单题、共同失败题和某个单模型已经很强的题。不能只收“模型意见不同”的题，因为它会人为放大异构组合的收益。

### 4.1 每个任务同时带“能力标签”和“耦合标签”

能力标签：理解需求、代码定位、实现、数值计算、证据检索、约束推理、边界验证、交付整合。

耦合标签：可独立分解 / 需要少量交接 / 强顺序依赖；另记上下文长度、工具种类、关键约束数量、答案是否唯一。

标签依据任务结构人工标注，不依据某个模型是否做对。记录合理的子任务依赖图或清单即可，不强迫 Agent 按标准分解执行，也不规定唯一解题路径。

对综合题可额外设计可单独评分的子能力探针，例如“定位错误”“指出边界条件”“验证修复”。探针是诊断实验，不算新的独立综合任务；同一题及其探针、变体必须属于同一家族、同一数据分区。

### 4.2 数据来源

建议以项目真实需求和自建可验证任务为主，以公共基准补足可比性：

- **真实需求回放**：从历史需求 / bug 中提取最初问题与故障前快照，去掉后续讨论、补丁和答案。优先尚未公开的新需求，必要时匿名化。
- **可程序生成的约束题**：从参数和规则生成输入，再由独立参考实现求解；参数种子和生成器版本冻结。同一生成模板的题目按家族处理。
- **公开基准**：可参考 [SWE-bench](https://www.swebench.com/) 的真实仓库 issue 修复任务；[LiveCodeBench](https://livecodebench.github.io/) 的代码生成、执行、修复与按发布日期组织题目的方式；[GAIA](https://arxiv.org/abs/2311.12983) 的推理与工具使用任务。

公共基准并非为本项目的异构协作结论背书。选题前核对任务许可、数据版本、模型可能见过的内容与可复现环境。闭源模型训练数据未知时，不能保证“未污染”。

把公开题改成离线资料、缩小仓库或替换工具后，应命名为自定义改编集，不能把分数直接当作原基准成绩。V1 不建议把依赖实时网页变化的题目混入主要对照。

### 4.3 一道题从需求变成可评测样本的流程

1. 固定真实问题与初始 fixture，写出模型可见的需求和交付契约。
2. 人工确认需求可解，提供参考实现或可接受答案集合；允许存在多个正确实现。
3. 写独立验收器：正确实现通过，已知错误实现失败；测试不绑定参考补丁的具体写法。
4. 写公开示例和私有边界测试；私有测试与答案只挂载给评分进程。
5. 标注能力、依赖、输入长度、来源与家族；以整个家族划分开发 / 锁定集。
6. 在开发集上试跑各模型的 A / B，修复歧义和有问题的评分器；不因为大家都错或没有模型差异就删除有效题目。
7. 冻结正式题目、配置、预算与验收器，再跑团队实验。正式成绩不能反过来影响收题或改答案。

模型可以辅助生成候选题和反例，但不能由某个参评模型生成答案后直接当唯一真值；必须有独立工具或人工验证。

## 5. 一个完整的样本例子

**任务：修复一个带过滤条件的游标分页接口。**

模型可见材料：小型 FastAPI / SQLite 仓库、接口规范、现有公开测试和复现请求。明确要求稳定排序、过滤后分页、已有字段兼容、非法游标返回指定错误、相同时间戳不漏项、不重复。

交付：工作区中的代码补丁；不以“说明自己修好了”的最终文本计成功。

私有验收示例：

| 检查 | 失败可说明什么 |
| --- | --- |
| 无过滤条件时已有测试继续通过 | 修改破坏兼容行为 |
| 多条记录时间戳相同时，跨页不重不漏 | 只按时间排序，缺少唯一 tie-breaker |
| 应用过滤后遍历所有游标页，结果集合正确 | 过滤与分页的执行顺序错误 |
| 非法游标、空结果、最后一页的返回符合规范 | 边界或接口约定遗漏 |
| 数据库查询有确定排序，输出符合公开 schema | 交付不能稳定使用 |

能力标签：规范理解、查询逻辑、代码实现、边界检查、回归验证。依赖标签：定位与修改有顺序依赖，边界验证可独立提出。

该题不预设“模型 M1 写实现，M2 找边界”。先看各模型独立产物的测试通过向量，再检查团队是否整合了不同模型发现的正确证据。

若 Mi 单独正确，而 Mj 的建议使最终补丁失败，这是负协作；若检查者发现了初稿遗漏且最后正确修复，是可追溯的纠错案例。单个案例仍只用于解释，因果收益依赖成对重复对照。

## 6. 先测能力矩阵，再测是否把互补变成收益

开发集上让 M1 / M2 / M3 分别执行 A 与 B，得到每道题与每项子验收的结果向量。不要只保存总分，否则无法区分“都拿 80 分，但错在不同地方”。

能力矩阵建议记录：

```text
task_id / family_id / capability_tags
model_id / version / strategy / replicate
success / quality / per_check_results
latency / usage_by_model / cost / missing_usage
```

开发集观察到的类型可作为假设：

- **共同成功**：所有模型都能完成；团队重点看成本与改错。
- **单成员优势**：某个模型稳定完成；团队能否保住正确结果。
- **部分互补**：各模型完成不同子验收；团队能否合成为全通过。
- **共同失败**：没有模型完整完成；团队是否出现新的完整解法。

这些类别与稳定性需靠重复验证；不能凭一次作答贴永久标签。锁定集不能只抽“部分互补”题；如果另建这样的挑战集，必须单独命名和报告，不混进整体分数。

### 6.1 额外诊断：谁能纠正谁

在单独审查套件中，把固定候选答案交给不同模型检查与修订：候选包含正确答案、自然错误答案、人工植入且独立验证的错误答案。隐藏来源模型与正误标签，保留必要的证据。

建立“候选来源 × 审查模型”矩阵，分别报告错误修复率和正确答案被改坏的比例。自然答案中某种错误不存在时记不适用，不为凑矩阵捏造该模型的失误。

它测试跨模型纠错关系，不代替端到端团队评测。候选来源、长度、错误类型需要平衡或分层报告；不能把错误更简单误判为审查者更强。

## 7. 成本与时间：异构实验不以总 token 作为公平标准

不同模型 tokenizer、推理用量和缓存定义可能不同。主图应是**任务成功率—费用—延迟**，token 按模型分别列出，不能把“相同总 token”当作等算力证明。

推荐冻结多个全任务费用档与截止时间，按每档分别比较 A/B/C/D：所有成员、检查、动态接力、失败尝试和汇总调用共享总预算，不能给每个模型各一份完整预算。具体金额在模型池与开发集校准后确定，不在本文猜测价格。

同一费用档内不要求各组实际花费完全相同；报告资源上限和实际开销。不同推理强度无法简单数值对齐，应固定各模型配置或明确把它作为另一个实验因素。

CLI 套餐无法提供完整费用时：

- 有完整 token 与明确费率时，可以报告版本化标准化估算费用，标明非实际账单。
- 用量缺失时保留未知；不得把 `chars/3` 用于严格跨模型等预算结论。
- 无法严格计费的实验只报告时间约束下的产品效果与观测用量，不声称完成等费用证明。

D 的额外回合仍需 B6 / C6 对照；E 的三个独立答案和最后汇总全部收费。超预算、超时与无有效交付均进入失败分母，评分费用另列。

## 8. 指标与结论边界

沿用总体设计的任务成功、部分质量、成本、延迟、置信区间与失败分析；增加下列异构诊断。

| 指标 | 定义与限制 |
| --- | --- |
| 相对单模型基线增益 | 团队成功率 − 开发集预选 B* 成功率；完整报告 B1/B2/B3，不能只呈现最弱基线 |
| 组成收益 | C-het − 配对 C-hom；依赖预登记排列分布，不自动等价于“多样性独立贡献” |
| 交流收益 | C-het − E；模型调用组成一致且资源上限一致，策略步骤与实际成本仍需展示 |
| 路由收益 | 团队 − R；检验选一个合适模型是否已经足够 |
| 成员信息保留 | 单模型可独立完成、团队却失败的配对比例，附最终交付变化 |
| 新增解决 | 同批独立 A/B 样本都未成功而团队成功的比例；附重复稳定性，不能声称单模型永远解不了 |
| 子验收互补 | 成员分别通过的子检查是否在最终产物全部保留；子检查成立不代表联合约束一定成立 |
| 审查损害 | 正确候选经审查后失败的比例；按来源、审查者和错误类型分层 |

单题事后选择最佳单模型输出可以报告为“观测样本的理想选择参考”，它使用了答案信息，不能作为可部署策略，也不是团队能力的理论上界。

所有团队 run 都按分配条件分析，不能只统计 D 实际发生 A2A 的子集。统计按任务家族配对聚类；重复调用不是新的独立题目。增加模型和预算档会增加比较数量，需预登记主比较，其他结果标为探索性。

评委尽量使用确定性验证。开放题需匿名输出、冻结 rubric 与人工抽查；如果评委模型属于参评模型池，明确披露并用独立评分来源复核，防止模型风格偏好影响结论。

## 9. 对现有 MVP 的增量

本次阅读的现有实现有 12 个 pilot 题、关键词/格式 rubric、单 Provider 统一选项；它可以先做闭卷探索，不能直接承担严格异构能力结论。

建议按顺序扩展，不改写或删除现有 pilot：

1. **模型清单与实验 manifest**：角色到具体模型快照的映射，区分 CLI 与模型，保存每次真实调用的实际配置。
2. **任务 schema**：新增 `family_id`、`split`、来源、能力/耦合标签、fixture 引用、公开交付契约与隔离评分器引用；与现有 `eval/tasks.json` 可兼容迁移。
3. **验收插件**：保留精确 JSON / 数值检查；新增隔离仓库测试、文件快照、证据槽验证。关键词只能作必要条件，不能替代正确性。
4. **实验条件**：新增模型组成与映射排列，防止 resume 时把同一 task/arm/repeat、不同模型配置误认为同一 run。
5. **资源采集**：逐模型、逐 attempt 用量和费用、总墙钟时间、缺失状态；不以字符估算补齐严格比较。
6. **诊断输出**：每项子验收向量、阶段产物快照、跨模型纠错矩阵、组成对照、独立汇总与路由对照。

运行唯一键至少包含：任务版本、策略、模型映射、人格配置、预算档、提示词/评分器版本、repeat；恢复运行时核验 manifest 一致。

### 9.1 推荐实施规模

- 起步：12 个开发任务先跑三模型的 A / B，每项 2 次，共 144 runs。用于能力画像、预算校准和验收器修复，不形成正式能力结论。
- 核心评测：48 个锁定任务 × 10 个条件 × 3 次 = 1,440 runs，先选一个冻结预算档。六种异构排列在八类任务内各出现一次，同时保持 lead 平衡。
- 资源有限：先做 24 个独立锁定任务的探索，并明确排列与类型无法完全交叉平衡；不要只删掉失败或模型差异小的任务。
- 确认协作机制：需要时追加 E / R 与计算量对照，仍使用完整锁定集；若依据初次结果调了策略，改用新的锁定集确认。

第一轮最值得得到的结论是：**哪些任务存在可利用的模型互补，当前工作流能否保留这种互补，以及它比选一个合适模型多付出了多少成本。**
