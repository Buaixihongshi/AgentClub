> 后续进展：工具 schema 与回复消息关联已修复，真实双向协议、自主求助及无需帮助对照均已验证；LiveCodeBench 小题集及执行评分器已准备。见[后续执行报告](2026-10-19-a2a-verification-and-open-code-pilot.md)。本文保留复盘时的状态，完整编码能力对比仍未执行。

日期：2026-10-19。状态：首轮记录已复核；V2 为待实现方案，尚未启动新模型调用。

## 1. 修正本轮实验的定位

本轮完成了真实 CLI 接入、用量采集、确定性评分和成本账本的冒烟验证，**没有完成最初提出的 Multi-Agent 能力、异构模型互补或实际 A2A 收益评测**。

实验从总体设计缩减为低成本试跑时，保留了 A/B/C/D 的名称，却没有保留足够的任务难度、机制覆盖和归因对照。这是实验设计与验收的问题，不能把未测出收益解释为协作机制无效，也不能把全通过当作能力评测完成。

首轮结果应标记为 **infra/cost smoke / A2A not exercised**。保留原始结果，不补写不存在的 A2A，不把离线 fixture 的接力计入真实模型实验。

GPT 和 Flash 的缓存输入比例、CLI 提示开销不同。不能用本轮缓存计价结果推导模型的普遍成本排名。完整数字见原批次 `comparison.md`、`calls.jsonl`、`analysis_pricing.json`。

## 3. 为什么没有测到预期内容

### 3.1 任务发生了天花板效应

两题都很短，全部必要信息一次性提供，单模型一回合即可正确完成；8 个多轮初稿已经全对。检查者无需补充关键证据或修正错误，动态委派缺少可观察的价值空间。

题目适合检查接入与格式，不能代表复杂调试、跨资料整合或任务分解。六题开发包只跑了其中两题，不能以“已设计六题”替代“真实执行两题”。

### 3.2 D 是固定流程加可选邀请，不是按需组队

`backend/app/orchestration/strategies.py` 中 C、D 都是：

```text
P1 起草 → P2 检查一 → P3 检查二 → P1 最终修订
```

D 只多一个允许邀请的开关，仍必须支付四个基础回合。它无法通过“不需要协作就直接结束”展示动态策略的成本优势。

共同起草提示还明确写着：“先不要自我评价，也不要邀请其他角色。”检查回合只要求列问题，最终修订是 closing，宿主会冻结该回合的新 A2A。最自然的委派入口受限，其他成员又已有固定发言安排。

对尚在固定工作流中的目标，`fire_and_forget` 请求还会被吸收为 `a2a.skipped`。这是需要单独测试的调度语义；本轮没有请求，不能把它认定为本轮零调用的直接原因。

### 3.3 工具契约存在具体不一致

复查时 `backend/app/mcp/server.py` 的 `invoke_agent` 描述和 Runner 提示支持 `wait_reply`，处理器和内部工具也支持该模式，但对 CLI 暴露的 schema 是：

```json
{"mode":{"enum":["fire_and_forget"],"description":"G3 只支持 fire_and_forget。"}}
```

`backend/tests/test_mcp_server.py` 还断言这一旧枚举。这意味着仅检查“D 有 invoke_agent 工具”和进程内模拟接力，无法验证真实 CLI 能按 schema 发起等待恢复。

这是下一轮前必须修复的接口缺陷，足以说明真实 `wait_reply` 尚未被合格验证；**它不能单独解释所有 A2A 为零**，因为 `fire_and_forget` 仍在 schema 中，而模型也没有尝试调用它。原运行快照未单独保存 MCP server 的文件指纹和实际 `tools/list` 返回，下一版须补齐。

### 3.4 预算契约没有完全落地

原设计要求额外宿主回合计数包含 `a2a_resume`，并为完整往返预留资源。当前 Runner 的 `a2a_used` 只在 `origin == "a2a"` 时增加，`a2a_resume` 不增加；`max_turns` 约束声明工作流，不是全部宿主调用的硬上限。

因此“最多两次邀请”“最多两个额外宿主回合”“完整 wait_reply 往返占两个槽”不能混用。当前计划表中的 D 最多 6 回合，不能仅靠这些字段保证。此次零调用未触发问题，但在启动下一轮前必须统一预算含义。

### 3.5 缺少收益归因对照

本轮 C 使用 Flash → GPT → Flash → Flash，与 B-Flash 相比，同时改变了身份和模型组成。没有 C-hom，无法区分多身份与引入 GPT 的作用。

没有等资源追加检查、独立答案汇总或只选模型的对照，不能把未来的任何提升直接归因于交流。两个模型、两题、每条件一次，也无法推断稳定的任务分层规律。

## 4. 本轮结论应如何表述

可以报告：两款 CLI 在修复审批配置后完成了这批试跑；36 回合有用量；两题所有条件通过；额外轮次增加了本批耗时和估算成本；当前 D 策略在两题上未发起 A2A。

不能报告：Multi-Agent 没有能力收益、异构协作没有互补、A2A 执行无效、D 动态路由比 C 更省钱、GPT 在一般场景下一定比 Flash 便宜。

零调用仍是“当前开放 A2A 的策略在这两题上的使用结果”，不应删掉 D 样本。它可以用于评估这套策略的总体表现，但不能估计**实际执行 A2A**的增量效果。只挑调用过 A2A 的题与其他组比较，也会引入选择偏差。

## 5. 下一轮先拆开两个问题

### 阶段 P：真实协议探针

只回答“实际 CLI 能否完成 A2A 往返”，不计入能力排名。

先在离线子进程 MCP 路径测试 schema、请求、队列、恢复和预算，再运行两个真实探针：

| 探针 | 请求者 | 受邀者 | 预期 |
| --- | --- | --- | --- |
| P1 | Flash | GPT | 显式调用 wait_reply，返回后由 Flash 提交带受邀者回执的结果 |
| P2 | GPT | Flash | 相反方向完成相同协议 |

探针允许任务明确要求调用工具，因为测的是协议遵循。使用独立的三回合探针流程：请求者 → 受邀者 → 请求者恢复，预计共 6 个宿主回合。现有四步 D 不能直接冒充这个流程，需先实现专用入口。

每个探针必须具备：

1. 持久化实际 `tools/list`；`mode` 枚举包含 wait_reply，目标 ID 正确。
2. 存在 `tool.call(invoke_agent)`、`a2a.request`、`a2a.invoke`。
3. 受邀者实际启动并发布回复，记录可关联的 turn/message ID。
4. 存在 `a2a.reply` 和调用者恢复回合；恢复输入包含对应回复，最终结果采用可验证回执。
5. 所有宿主调用有用量；未超出总调用预算；失败保留原尝试、不自动追加付费重试。

强制协议探针通过，只证明链路可用，不证明协作让题目做得更好。`fire_and_forget` 的入队、已排班吸收、closing 拒绝，以及嵌套、超预算、失败恢复先以离线用例覆盖。

### 阶段 U：可自主选择的策略对比

V2 保留六个条件名对应的模型基线，但 D 明确换成新策略，不能与 V1 混合统计：

| 条件 | 定义 |
| --- | --- |
| A-Flash / A-GPT | 各自一回合自主求解和交付 |
| B-Flash / B-GPT | 各自起草、检查、再检查、修订，4 回合 |
| C-mixed | 保留固定 Flash → GPT → Flash → Flash，4 回合 |
| D-mixed-v2 | Flash lead 首先决策；可直接交付，或选择成员处理明确子任务，收到回复后继续或交付；不预先排齐所有成员 |

D 的初始轮不能标 closing，也不能要求“不要邀请”。只有选择最终提交时才关闭协作。向模型提供可调用成员 ID、模型配置、已有结果、可用模式及剩余资源；不声称某品牌天然更擅长某类题。所有条件看到相同的任务信息和工具说明。

阶段 U 不强制 D 调用。简单题不调用是合理结果；复杂题仍全部不调用时，报告“此版本未使用委派”，保留整批结果，回到开发集检查策略，不能在锁定题上临时改提示直到邀请出现。

## 6. 小范围任务集：四类任务，各一题先试

每类准备独立开发题和锁定题；先在开发题确认输入、评分器和难度，冻结策略后才运行锁定题。不能只保留出现模型分歧或协作获胜的题。

| 家族 | 具体输入和交付 | 确定性验收 | 观察什么 |
| --- | --- | --- | --- |
| U1 简单负对照 | 短记录筛选、唯一规则、JSON 结果 | 精确字段和值 | D 是否直接结束；固定协作的额外成本 |
| U2 边界调试 | 小型纯函数、行为契约、常见错误实现；输出统一格式修复补丁 | 私有正常/边界/回归测试，分别列结果 | 复核是否修正初稿，是否引入新错误 |
| U3 冲突证据综合 | 约 10–15 条离线变更、撤销、生效时间和申请记录；输出配置及来源 ID | 生效状态、时间范围、来源、不可确定字段 | 委派能否补证或纠正相互附和 |
| U4 组合约束交付 | 约 8 个任务、依赖、人员能力、工时和截止期；输出排程与约束报告 | 可执行约束检查；可行性与目标值分开 | 分解与整合是否有收益，交接是否丢约束 |

U2 的评分在独立执行环境检查最终补丁，模型不能读取隐藏测试；执行权限与反馈渠道对各组一致。补丁执行需隔离，不能直接在宿主执行任意模型代码。U4 不要求匹配唯一标准排程，满足约束的等价解应通过。

除整体成功外，记录子检查分、首次交付正确性、改错/改坏、违反的硬约束和证据定位。不能只做关键词计分，也不能因初稿全对而人为制造错误给协作组修复。

所有组拥有相同原始材料与访问能力。若额外设计“只有另一位 Agent 持有某条信息”的任务，应归入分布式信息协议集；单 Agent 需有等价资料访问能力，才可作能力公平比较。不给 D 单独增加隐藏资料或专属工具来制造优势。

四道锁定题 × 六条件 × 一次 = **24 次探索运行**，不是确认性统计结论。一次采样只用于找失败链路与估算开销；扩样必须覆盖预登记家族，不能只重复协作获胜的题。人格保持中性，角色人格实验单列。

## 7. 预算与异构归因

### 7.1 先给机制留预算，再决定能力批次规模

下一轮使用独立预算，不自动沿用旧版 $5 或重置累计费用。计划、已花、历史未知用量分别报告；先出离线成本计划，执行时沿用完整账本。

每题所有策略共享同一最大资源上限，报告实际使用量；允许早停，不强迫花完。D 的受邀者和请求者恢复都算宿主调用，建议首版每题总计最多 6 个，最多两个完整等待往返，禁止嵌套委派；超额请求在执行前拒绝并记录。B/C 的四步与 D 的自适应停止仍是策略差异，主比较评估的是策略总体收益。

24 次核心运行最多约 80 个宿主回合，加两个三回合协议探针共 86 个。这个上限只有在统一调用预算实现后才成立，不是当前 Runner 的保证。美元费用另按实际 CLI 开销预估，不能再次使用被首轮证伪的每回合 12k 输入假设。

调用间软停止仍无法封顶正在执行的一次 CLI 请求。预留完整往返与最终提交开销；缺用量立即停止。用缓存前、缓存后两种 API 等价估算，CLI 实际账单未知则继续标未知。

### 7.2 逐级回答问题，避免一次跑满矩阵

24 次核心运行先回答“这两种具体 CLI 配置下，哪套策略在这些任务上更实用”，尚不能单独归因于异构模型。

若要继续回答“不同模型协作本身的增益”，在同一锁定任务集按预登记规则补 C-hom-Flash、C-hom-GPT，各 4 回合：异构 C 与两种同构 C 比较；同构 C 与相应 B 比较。不要只在异构获胜的题上补对照。

要声称动态路由机制带来提升，还需同模型组成、同总资源上限的固定追加检查对照。若 C/D 超过强单模型，再补独立作答后汇总和只选模型的对照。未跑的归因实验明确列为“未回答”，不以有限预算省略后仍声称已证明。

成员映射和 lead 暂固定为首轮配置以控制成本；模型角色互换另做预登记小实验。当前模型组成、CLI、缓存和上下文处理仍共同影响结果。

## 9. 离线复查方式与本次交付边界

```bash
.venv/bin/python scripts/audit_real_pilot.py \
  --input output/eval/real-pilot-20261019-round1-r3 \
  --output output/eval/real-pilot-20261019-round1-r3/retrospective-audit.json
```

输出路径需不存在；省略 `--output` 可重复打印复查结果。原始 `manifest.json`、`trials.jsonl`、`calls.jsonl` 和数据库保持不变。

本次交付为真实记录审计、结果定位修正和 V2 设计。上表工程改动、新任务、协议探针与下一轮付费运行尚未实施。旧版 spec 和 pilot 保留作为历史设计，在入口增加本复盘链接，避免把目标设计当成已完成能力。
