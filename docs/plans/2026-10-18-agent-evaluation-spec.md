目标：判断什么任务值得协作、什么任务应该保持单 Agent，以及动态 A2A 是否值得它的额外成本。

## 1. 要回答的问题与交付物

不以“证明 Multi-Agent 一定更好”为验收标准。允许得到“没有可靠收益”“只在部分任务有效”“多数情况下不划算”的结论。

本设计将“不同人物”拆成两个维度：**不同任务类型**与**不同角色人格**。前者是主实验的分层依据；后者单独实验，避免把人格差异当成架构收益。

评测最终交付：

1. A / B / C / D 的成功率、质量、成本、延迟与置信区间。
2. 按任务类型划分的收益与退化矩阵，明确哪些结论证据不足。
3. 可以回放的失败案例：错误从哪里进入、在哪次交接传播、最后为何未被修正。
4. 一份路由建议：什么时候用 A、B、C、D；无法判断时保留默认基线。
5. 可复跑的任务集、配置快照、评分器与原始记录。

暂不包含：前端实验中心、线上自动切换策略、并行 Agent、训练模型、全局人格重构。先补评测基础设施，再决定产品改造。

## 2. 当前代码提供了什么，以及尚缺什么

以下为本次阅读工作区代码得到的现状，不代表能力实验结论。

| 位置 | 当前行为 | 对评测的影响 |
| --- | --- | --- |
| `backend/app/orchestration/complexity.py` | 按关键词、长度等判断复杂度 | 不能用这个标签充当难度真值；主实验必须显式指定策略 |
| `backend/app/orchestration/speaker.py` | 简单任务 1 轮、中等 2 轮、复杂为配置顺序发言后首位收尾 | 当前不是统一的固定协作基线；各任务可能根本没用多 Agent |
| `backend/app/orchestration/runner.py` | 串行执行，动态队列优先，支持调用者恢复，收尾后冻结 A2A | 可以复用执行机制；动态 A2A 不等于并行加速 |
| `backend/app/mcp/tools.py` | 支持 `invoke_agent` 的两种模式；部分重复请求被吸收 | 必须区分申请、接受、跳过、实际执行，不能把申请数当协作次数 |
| `config/agents.json` | 三位人格默认主 Provider 不同 | 直接用默认设置对比会混入模型差异 |
| `backend/app/orchestration/context.py` | 默认历史最多 8 条、单条 1,200 字符、合计 6,000 字符 | 多轮更易遇到裁剪；需记录可见上下文及裁剪情况 |
| `runner.py` 的 `_build_prompt` | 所有角色已有发送前自检，并引导 A2A | A 不是“绝无内省”；B 必须定义为显式额外反思回合；非 D 需屏蔽 A2A 引导与工具 |
| `backend/app/adapters/stream_events.py` | 定义 token、缓存、推理 token、费用等用量字段 | 有字段不代表每个 Provider、每次失败都能完整上报 |
| `backend/tests/` | 已覆盖编排、A2A、失败、共享历史等工程行为 | 可验证协议正确，尚不能说明协作提高任务成功率 |

尤其不能直接把 `max_turns` 当统一模型调用预算：任务模式中它限制声明工作流推进，A2A 调用和 `a2a_resume` 还会产生额外轮次；CLI 一轮内部也可能多次访问模型。

也不能仅靠 `max_a2a_invocations=0` 关闭协作：目前进程内与子进程持久化路径对零值的处理不同。需要在工具暴露和宿主执行两层显式拒绝。

## 3. 假设与实验边界

| 假设 | 主要比较 | 可能支持它的证据 | 可能推翻它的证据 |
| --- | --- | --- | --- |
| H1：显式反思能修正初稿错误 | B − A | 隐藏检查成功率提高 | 改对为错、成本上升但无收益 |
| H2：换一个 Agent 比同一个 Agent 继续反思更有效 | C − B | 相同步数、相同临时任务下 C 更好 | 同质重复、错误沿袭、优势不稳定 |
| H3：动态协作策略比固定协作更有效 | D − C | 同预算上限下成功率或成本效率更好 | 无效邀请、循环、预算挤占最终交付 |
| H4：协作收益随任务特征变化 | 分层的 B−A / C−B / D−C | 某些预定义类型稳定受益 | 简单任务退化、强依赖任务交接损失 |

主实验识别的是**指定策略的总体效果**。D 如果用了更多推理资源，D−C 不能单独解释为“动态路由本身”的收益；需要第 5 节的追加对照。

## 4. 四组策略的精确定义

主实验使用同一个真实 Provider、同一个模型版本、同一个推理强度与工具集。主配置采用中性人格；三位 Agent 具有不同身份 ID，但能力、工具权限和基础指令相同。

每个宿主回合启动独立 CLI session，不复用隐藏 session 记忆。跨回合状态只来自显式消息、任务文件与产物；B 同样如此。单 Agent 的定义是单一执行身份，不是禁止使用工具或在一个 CLI 回合内自主完成多步工作。

| 组别 | 固定回合骨架 | 身份 | 显式反思 | 动态 A2A |
| --- | --- | --- | --- | --- |
| A：Single Agent | 直接解决并交付，1 个宿主回合 | P1 | 无额外反思回合；保留共同的基础自检 | 禁止 |
| B：Single + Self Reflection | 初稿 → 检查 → 再检查 → 最终修订，4 回合 | 全部 P1 | 两次显式检查，要求定位问题或说明无问题 | 禁止 |
| C：Multi Fixed | 初稿 → 检查 → 再检查 → 最终修订，4 回合 | P1 → P2 → P3 → P1 | 与 B 相同的临时回合目的 | 禁止 |
| D：Multi + Dynamic A2A | 与 C 相同的 4 回合骨架，允许插入动态接力 | 同 C | 同 C | 最多增加 2 个宿主回合 |

检查回合只要求基于证据检查正确性、遗漏及约束，不强制“找出问题”或制造分歧。四组使用相同最终交付契约和相同任务工具权限。人格不绑定“规划 / 执行 / 审查”工种。

### 4.1 D 的边界

- 支持现有 `fire_and_forget`、`wait_reply`；不增加主持器或额外路由模型。
- 每个实际被执行的受邀者回合占 1 个动态槽，`a2a_resume` 也占 1 个。因此一次完整 `wait_reply` 往返占 2 个槽。
- 入队时原子预留完整往返槽位；不允许只执行受邀者却没有预算恢复调用者。
- 固定最终修订回合不接受新邀请；保留现有收尾冻结语义。
- 采用当前重复邀请吸收规则，分别统计 `skipped` 与真正执行。被吸收不等于发生额外协作。
- D 可以一次都不邀请；不能为制造实验差异强制它调用 A2A。报告实际使用率，低使用率也是结果。
- 每轮可读取剩余预算。A / B / C 同样能看到自己的预算；只有 D 看到可用的动态槽。

### 4.2 任务最终输出

每个样本只有一个被评分的最终版本：任务声明的答案文件或交付目录快照。最终回合通过公共提交接口登记文件、版本与哈希；不得事后从多条消息中挑选最好答案。

超时前已经登记的版本仍可做诊断评分，但“在预算内有效交付”才可能成功。`MissionStatus.COMPLETED`、CLI exit 0 或说“完成了”均不能代替任务成功判定。

## 5. 公平性：同时报告预算约束与实际花费

### 5.1 主实验：相同资源上限

同一任务的四组拥有相同的累计 token、墙钟时间、工具权限与输入信息上限；不要求浪费资源以花完预算。策略的固定步数与实际资源使用可以不同。

开发集先校准 small / medium 两档预算，再冻结正式清单；任务的预算档位由人工标注与可验证工作量决定，不由现有关键词分类器决定。试运行起点如下，**不是最终实验参数**：

| 档位 | 全 run 累计模型 token 上限 | 全 run 墙钟上限 | 宿主回合硬上限 |
| --- | --- | --- | --- |
| small | 24,000 | 180 秒 | 6 |
| medium | 80,000 | 600 秒 | 6 |

token 以模型原生用量定义归一：输入含缓存读取；输出若已包含推理 token，不重复相加。跨 Provider 不直接合并原始 token 成一个可比成本数。

预算统计涵盖整个任务的所有模型子请求、复核、工具后续推理、失败尝试；评委的成本单独报告。全局墙钟包含 CLI 启动和编排开销，不包含评委评分时间。

预算守卫在每次可控调用前预留、调用后核算；到限停止，保护最终提交所需资源。需明确能力等级：

- `hard`：Provider 能约束每次内部请求并给出完整用量，可进入严格等预算结论。
- `posthoc`：只能在宿主回合结束后核算；超支计失败并报告超支量，不声称运行时精确等预算。
- `unknown`：内部模型、用量或隐藏子 Agent 不可观测；只进入产品配置对照，不能进入严格成本比较。

先验证所选 CLI 是否支持对应约束。不能把文本提示里的“请节约 token”当硬预算能力，也不能以字符数冒充实测 token。

### 5.2 必要的计算量对照

B 与 C 均为 4 个宿主回合且阶段目的一致，是主实验中最直接的“持续自检 vs 身份切换”比较。

D 可以比 C 多 2 个回合。如果 D 有收益，必须追加 B6、C6：在最终修订前固定增加两次检查，沿用同一全局资源上限。B6 使用 P1；C6 的额外检查者预先指定为 P2、P3。

这些是 B / C 的预算消融变体，不替代四个核心组别。对正式任务全量运行追加对照后，才讨论 D 相对“更多固定检查”的优势。只跑案例子集时，仅得出该子集的探索性结论。

若需要宣称 C 优于“同等计算量的普通单 Agent”，还需增加 A 的多回合继续工作变体：给同一个 Agent 相同步数继续解决任务，不规定反思阶段。A 一次调用与 C 四次调用的比较本身无法隔离协作机制。

### 5.3 必须冻结的条件

| 因素 | 约束 |
| --- | --- |
| 模型 | 记录并核验模型实际标识、版本、推理强度、CLI 版本；无法锁定时明确标注 |
| Provider fallback | 主实验关闭；失败不降级到另一模型或 fake；产品对照另跑 |
| 工具 | 相同版本、允许列表、文件访问范围、联网规则；禁用 CLI 自带隐藏 sub-agent / delegation |
| 初始状态 | 每个 run 新 conversation、数据库、任务工作区、CLI session；任务 fixture 内容一致；隔离用户全局记忆、skills 与隐式项目指令，仅加载冻结的公共指令 |
| 可见信息 | 四组有权读取相同完整输入；不能只给 D 额外参考答案、专家知识或检索源 |
| 历史策略 | B / C / D 使用相同共享历史构建规则；记录实际裁剪，不给 B 隐藏长记忆 |
| 人格与顺序 | 主实验中性；P1 / P2 / P3 与真实角色 ID 的映射按预定顺序平衡，四组配对一致 |
| 状态污染 | 克隆相同初始 fixture，任务内共享修改，跨 run 清空；缓存策略记录且执行顺序随机 |
| 运行环境 | 同一时段分块、同一机器与并发限制；主实验 run 串行，避免竞争本机资源 |
| 重试 | 不因答案差而重试；外部故障按预定义分类处理，所有原始尝试保留 |

原生工具若仍能绕过 MCP 启动其他 Agent，A / B 就不是有效单 Agent 对照。此项不能仅依赖提示词，需要工具或执行权限约束；做不到的 Provider 标注不适用于该主实验。

## 6. 任务集：主动寻找退化边界

V1 目标为 60 个独立任务：12 个开发任务、48 个锁定任务。锁定集每类 6 个。任务间相似改写、同一代码模板和同一源文档的变体属于一个任务家族，必须整体分到开发集或锁定集，不能泄漏。

每个任务预先标注：类型、难度、可分解程度、子任务依赖程度、输入长度、约束数量、验收方式、预期交付格式。协作是否“应该有效”只能作为待检验标签，不能根据实验成绩回填。

| 类型 | 具体样本方向 | 客观验收重点 | 希望发现的边界 |
| --- | --- | --- | --- |
| T1 简单确定性 | JSON 转换、短文本抽取、单一规则变换 | 精确匹配 / schema / 约束 | 过度思考、格式破坏、多轮改错 |
| T2 局部代码修复 | 小函数边界 bug、已有实现补兼容 | 隐藏测试与原行为回归 | 看似合理的改动引入回归 |
| T3 可分解交付 | 多个独立模块、接口和文档配套 | 子任务通过率与整体契约 | 多视角覆盖能否抵消交接成本 |
| T4 强依赖推理 | 多步排程、依赖顺序、组合约束 | 可执行约束检查器 | 交接后前提丢失、局部正确整体错误 |
| T5 证据综合 | 离线资料包中存在相互冲突陈述 | 事实槽、来源定位、冲突处理 | 无证据共识、错误被重复放大 |
| T6 长上下文 | 关键条件分布在开头、中间、末尾 | 约束召回与交付一致性 | 历史裁剪、摘要失真、遗忘 |
| T7 方案与权衡 | 有明确需求、预算和禁用条件的设计 | 约束检查 + 冻结的人工 rubric | 文笔更长却不更可执行 |
| T8 歧义与证据不足 | 缺必要参数、资料无法支持唯一结论 | 是否承认不确定、合理澄清 | 多人讨论后把未知说成确定 |

T8 使用固定交互脚本：所有组在同一澄清工具中获得同样的预定义回答，不由现场用户临时决定。脚本和任务输入分离；只有调用正确澄清才返回相应信息。澄清不增加额外宿主 Agent 回合，消耗的时间和模型推理照常计入。

V1 以封闭资料和可复现代码 fixture 为主。网络搜索、真实仓库大改、用户中途插话放到后续套件，避免一次引入太多变化。

### 6.1 单独的压力与故障套件

不把人工故障混入主任务成功率。另设相同输入的成对压力样本：

- 输入资料中有可信口吻但错误的建议，检查是否独立核验；所有组都看到同一建议。
- 历史接近裁剪阈值，检查关键约束消失的位置。
- 工具返回超时、缺文件、格式损坏，检查错误是否被掩盖成“已完成”。
- A2A 请求重复、等待循环、恢复槽不足，检查是否按契约跳过或终止。
- 最终交付前预算即将耗尽，检查是否无产物或只留下讨论记录。

只对 D 生效的 A2A 故障用于验证 D 的可靠性，不拿来直接推导四组总体能力排名。

## 7. 评分：任务完成优先，过程指标用于解释

### 7.1 主指标

`success ∈ {0, 1}`：在预算和截止时间内提交有效交付，且满足该任务预登记的所有关键验收条件。

- 代码 / 转换 / 约束任务：以隐藏测试、精确检查和关键回归为准。
- 证据与方案任务：硬约束全部通过，且冻结 rubric 质量分 ≥ 80/100。
- 非法修改测试、读取评分密钥或未按契约交付，均判失败。
- 超时、阻塞、缺最终产物、预算超限均计入分母，不能只比较 completed 样本。

### 7.2 次指标

| 指标 | 定义 / 报告方式 |
| --- | --- |
| 质量 Q | 0–100，失败样本也评分；有部分产物时展示诊断质量，但不改写 success |
| 质量维度 | 正确性 40、完整性 25、约束遵循 25、交付可用性 10；每题有评分锚点 |
| 资源成本 | 输入 / 缓存 / 输出 / 推理 token、实际费用、模型子请求数、宿主回合数 |
| 延迟 | 任务总耗时中位数与 p90；成功样本耗时另列，不能替代全样本耗时 |
| 单次成功成本 | 所有 run 的总成本 / 成功数；无成功时报告不可估计，不填 0 |
| 退化率 | 配对任务中基线成功、候选策略失败的比例；同时报告反向改善率 |
| 稳定性 | 同任务重复的成功一致率、质量离散程度 |
| 预算违规率 | token 超限、时间超限、动态槽违规分别报告 |

美元费用缺失时记 `null` 并显示覆盖率。套餐用户的账面 0 元不等于推理无成本；可另给版本化单价估算，必须标为估算并保留定价来源与日期。缺失用量不能作为 0，也不能用不完整账单宣称更省。

质量分不能通过发言次数、篇幅、礼貌程度、角色辨识度或“大家同意了”加分。

### 7.3 协作诊断指标

- A2A：请求数、接受数、跳过数、实际受邀回合、恢复回合、等待失败、深度、模式和去重原因。
- 修订：初稿错误被最终版本修正的比例；初稿正确而最终错误的比例。A 无修订阶段记不适用。
- 信息：关键约束首次遗漏在哪一回合；被引用的结论是否有可追溯证据。
- 交接：受邀结果是否被后续交付使用，有无引用路径、文件哈希或答案字段变化支持。
- 重复：人工编码“没有新增可验证信息”的回合比例；文本相似度只作辅助信号。

“某次邀请有用”只能是诊断标注。单条 trace 上质量增加不等于邀请产生因果收益；需要对同样例进行禁用 / 替换该邀请的重复对照，且仅作后续实验。

### 7.4 评分隔离与盲评

隐藏测试、参考答案与评分 rubric 存在评分进程的隔离目录；不能放在 CLI 可读的仓库路径里。模型运行结束后，评分器只读最终产物副本执行检查，禁止执行产物里的任意评测指令。

开放题先做人工定标。模型评委只看到匿名化的最终交付与必要输入，去除角色名字、Provider 和策略标签；不看协作聊天，不按过程热闹程度评分。保留交付本身有意义的解释与限制。

评委模型与版本、rubric 哈希、判分证据必须记录。锁定集先由冻结评委评分；随机抽取 20%（向上取整）的输出做双人人工复核，关键成功 / 失败分歧全部复核。报告一致率与裁决原因；不能因为某组分低而单独换评委或改标准。

## 8. 实验运行与统计计划

### 8.1 分阶段运行

1. **离线连通验证**：fake adapter 检查策略步序、权限、预算和产物契约，不产出能力结论。
2. **开发集 pilot**：从 12 个开发任务中选覆盖八类的 8 个，每组重复 2 次，共 64 runs；校准预算、任务歧义和评分器。变更后冻结 task / prompt / scorer / config 版本。
3. **锁定集主实验**：48 任务 × 4 策略 × 3 次重复 = 576 runs。
4. **解释 D 收益的追加实验**：B6、C6 如全量各重复 3 次，再增加 288 runs。其余消融另计，不悄悄混入主实验结果。

这些数量是 MVP 的探索规模，不是检测某个微小提升的功效保证。先用开发集估计方差与最小实际收益的可检测性；样本不足时报告不确定，后续使用新锁定任务扩展确认。

### 8.2 配对与随机化

配对块为 `(task_id, replicate_id, model_snapshot, budget_profile)`。块内四组输入与环境一致，执行顺序用实验随机种子打乱；角色 ID 的六种排列在锁定任务间平衡，同一块 A / B 的 P1 与 C / D 的开场、收尾身份一致。

区分 `schedule_seed` 与 `model_seed`：前者可控制执行顺序；只有 Provider 真正支持时才设置后者。重复调用不能伪装成可复现的模型随机种子。

正式 run 中只收集，不看分数调参。第三方限流或机器故障保留原记录；主表按实际失败计入，另给按预登记规则排除外部故障的敏感性分析。协议 bug 导致不合规时整批标记无效，修复后以新实验版本重跑，不仅重跑差的一组。

### 8.3 如何下结论

- 预登记主比较：B−A、C−B、D−C，报告成功率差，单位为百分点，以及配对 95% 置信区间。
- 先在任务内合并 3 次重复，再按任务家族聚类重采样；按八类分层 bootstrap，避免把 144 次调用当作 144 个独立任务。若多个任务共用模板，按共同家族聚类。
- 同时给配对成功转移表：双成功、只基线成功、只候选成功、双失败。
- 若作显著性声明，对三项主比较使用配对随机化检验并做 Holm 校正，阈值 0.05；区间与效应量仍必须展示。
- 分类型结果样本少，默认探索性；事后挑出的优势类型不能称为确认性结论。
- 主表按分配策略分析：D 未调用 A2A 的 run 仍属于 D，不能只挑实际调用 A2A 的任务与 C 比较。每次重复都计成绩，不能用三次中最好的一次或“至少成功过一次”替代单次成功率。
- Q 差值、成本比值、延迟比值同样按任务聚类给区间。零成本或缺失费用时不计算无意义比值。
- “未显著”表示证据不足，不能解释为“两者等价”。

预登记一个产品决策起点：成功率至少提高 **5 个百分点**，且增量成功的成本落在事先给定的预算容忍范围内，才考虑升级默认策略。5 个百分点是可评审的目标值，不是统计事实；pilot 后、锁定实验前允许调整并记录。

预算容忍范围由使用场景显式给出，例如单任务截止时间与可接受费用上限；未定义时只展示成功率—成本—延迟的 Pareto 关系，不擅自折算为单一总分。没有一种策略同时在质量、成本、延迟上更好时，保留取舍。

## 9. 人格与真实产品配置的补充实验

主实验完成后再区分下列问题，不能把它们同时塞入第一轮：

| 实验 | 改动 | 保持不变 | 回答什么 |
| --- | --- | --- | --- |
| 人格实验 | 中性 → 张楚岚 / 冯宝宝 / 王也原人格 | 模型、权限、策略、预算 | 人格多样性有没有收益或退化 |
| 单人角色实验 | A / B 分别由三个人格执行 | 同任务、模型、预算 | 是否某位角色天然更适合某类任务 |
| 顺序实验 | 六种角色排列 | 模型、任务、策略、人格 | 开场 / 收尾身份是否影响结果 |
| 产品配置实验 | 使用当前默认异构 Provider、fallback、上下文策略 | 相同任务与评分器 | 用户当前真实配置的整体体验如何 |
| 上下文实验 | 当前裁剪窗口 → 更大固定窗口 | 其余条件相同 | 多 Agent 退化是否主要来自信息丢失 |

人格实验中的 A / B 必须遍历三个人格或按预登记方案平衡，不能只拿默认张楚岚与三人团队比较。产品配置实验的优势只能归于“整套配置”，不能归于多 Agent 架构本身。

补充实验先在开发集定位问题；若要形成正式结论，使用新锁定样本或预先声明的完整消融矩阵。每项单独报告样本规模与预算。

## 10. 实现设计

以下路径与接口为目标设计。当前 MVP 已使用 `eval/`、`backend/app/evaluation/` 与 `scripts/run_eval.py` 实现了其中的四组策略、12 任务 pilot、rubric 评分和配对报告；预算守卫、隔离 grader、锁定集与 B6/C6 消融尚未实现。

```text
evals/
  README.md
  configs/ablation-v1.yaml
  tasks/dev/*.yaml
  tasks/locked/*.yaml             # 可见题目与 fixture 引用，不含评分秘密
  fixtures/                      # 冻结输入、代码与离线资料
backend/app/evaluation/
  schemas.py                     # TaskSpec / ExperimentSpec / RunRecord
  policies.py                    # A / B / C / D 的显式执行策略
  budget.py                      # 全局资源与动态槽守卫
  harness.py                     # 克隆 fixture、调用 runner、采集与冻结产物
  telemetry.py                   # 用量归一、实际上下文、事件关联
  graders/                       # 评分器代码；私有答案由隔离挂载提供
  report.py                      # 配对统计、区间、失败索引
scripts/evaluate.py              # validate / plan / run / grade / report
output/evals/<experiment_id>/    # 本地结果，沿用现有 output 忽略规则
```

### 10.1 与现有 Runner 的接缝

为任务模式注入可选 `ExecutionPolicy`，默认仍走现有 `select_workflow`。评测策略提供初始步骤、工具允许列表、阶段目的、最终提交契约与动态配额，不通过改写用户 goal 来触发不同复杂度。

任务模式与圆桌模式分开评测。V1 只覆盖任务模式，避免让两个不同终止协议成为额外变量。四组都复用 `CLIAdapter`、Repository、MCP 发布路径和产物机制。

模型实际调用通过评测配置明确指定，不修改用户已保存的团队配置。测试场景只使用隔离数据库、工作区和 artifact_root。

公共提交接口只登记交付版本，不决定是否成功。评分由 Runner 外的独立进程完成，Agent 的 `update_status` 无权设置评测结果。

### 10.2 示例配置

```yaml
schema_version: 1
experiment_id: ablation-v1-pilot
suite: dev
strategies: [single, self_reflection, multi_fixed, multi_dynamic]
replicates: 2
schedule_seed: 20261018
provider:
  id: REQUIRED_REAL_PROVIDER
  model: REQUIRED_PINNED_MODEL
  reasoning_effort: REQUIRED_EXPLICIT_VALUE
  fallback: []
  native_delegation: disabled
persona_mode: neutral
context_policy: current_bounded_v1
budget:
  profile: small_pilot
  total_model_tokens: 24000
  wall_time_seconds: 180
  max_host_turns: 6
  dynamic_extra_turns: 2
  enforcement_required: hard
grader:
  version: rubric-v1
  secrets_mount: REQUIRED_ISOLATED_PATH
```

占位字段、不可用真实 Provider、无法禁用的原生 delegation、缺失硬预算能力应在 preflight 报错，不能自动替换为 fake。只有显式的离线验证配置允许 fake。

### 10.3 样本与记录契约

`TaskSpec` 至少包括：`task_id`、`family_id`、类型、开发/锁定分区、难度标签、输入、fixture 哈希、工具权限、预算档位、输出路径、公开交付 schema、私有 grader 引用。验收阈值在 Agent 可见输入中说明到完成任务所必需的程度，不泄漏隐藏样本。

`RunRecord` 至少包括：

- 身份：experiment / task / family / strategy / replicate / mission ID。
- 复现：Git SHA、脏工作区补丁指纹、任务与配置哈希、公共提示词与策略提示词哈希、CLI / 模型实际版本。
- 执行：开始结束时间、预算档、实际工具权限、步骤身份、终态、失败主因与次因。
- 资源：每个 attempt 的用量、来源与缺失状态；预算执行等级、超支量；评委成本单列。
- 输出：最终提交 ID、产物快照及哈希、隐藏测试结果、质量维度、评分证据与评分器版本。
- 关联：源事件 ID、parent invocation ID、step ID、turn ID、attempt ID；相同 A2A 从 request 到 invoke 只计一次逻辑请求。

新增或补齐结构化事件：`eval.run_started`、`eval.context_snapshot`、`eval.stage_submitted`、`eval.budget_updated`、`eval.final_submitted`、`eval.run_finished`、`eval.scored`。其中 context snapshot 保存实际可见消息 ID、裁剪位置、prompt 哈希与本地原文引用；不只保存 `prompt[:80]`。每阶段交付保存不可变快照，以便判断初稿是否被修正或改错，不能只保留被覆盖后的最终文件。

不依赖模型隐藏思维链评分或解释收益。过程分析使用可见行动、引用证据、简短决策说明、消息版本与产物变化。

所有失败 attempt 仍计资源；如果当前 adapter 的失败路径缺用量，要补齐采集或标为未知。Provider 原始用量记录保留，归一算法版本化，不能对“最后一条累计用量”和“逐条增量”重复求和。

### 10.4 运行入口与产物

建议 CLI：

```bash
python scripts/evaluate.py validate --config evals/configs/ablation-v1.yaml
python scripts/evaluate.py plan --config evals/configs/ablation-v1.yaml
python scripts/evaluate.py run --config evals/configs/ablation-v1.yaml
python scripts/evaluate.py grade --experiment ablation-v1-pilot
python scripts/evaluate.py report --experiment ablation-v1-pilot
```

`plan` 显示 run 数、预算上限、实际 Provider 与能力检查，不访问模型。`run` 只有显式真实评测配置才调用模型，仓库默认仍保持 fake。恢复运行根据已完成的 run key 去重，不能因恢复操作重新抽样策略顺序或挑选较好输出。

每次输出：`manifest.json`、`runs.jsonl`、`scores.jsonl`、`paired_results.csv`、`report.md`、`failures/`，以及按 run 保存的事件和产物快照。报告标注有效样本、失败、缺用量、不合规 run 数及所有排除原因。

原始记录默认留本地。公开结果包只包含匿名化任务、必要证据与脱敏配置，不包含账号凭证、CLI 全局配置或用户历史对话。

## 11. 最终报告应该长什么样

主表列 A / B / C / D，展示：成功率及区间、Q、累计 token、费用及覆盖率、耗时中位数/p90、超时率、单次成功成本。

分层表每行一个 T1–T8 类型，列 B−A、C−B、D−C 的成功率差与区间、成本变化、样本数及“受益 / 退化 / 证据不足”。无数据时留空，不预填预期赢家。

失败案例包含同一个任务的四组最终交付、验收结果，以及指向关键回合和证据的最短事件链。失败原因允许多标签，另选一个可操作主因：

| 主因 | 判定证据 | 可能的产品行动 |
| --- | --- | --- |
| 基础能力不足 | 多组均未通过同一关键检查 | 换模型 / 改任务支持范围 |
| 无效检查 | 新回合未产生可验证修正 | 降低固定轮数或回到 B / A |
| 错误传播 | 未核验结论被后续交付沿用 | 加证据引用与独立检查 |
| 上下文丢失 | 约束不在实际可见历史中 | 调整上下文策略 |
| A2A 编排失败 | 等待、重复、预算或恢复事件异常 | 修编排契约 |
| 过度协作 | 简单任务初稿正确，后续改错或超时 | 对该类任务优先 A |
| 最终收束失败 | 中间结果存在，最终未有效交付 | 保护提交预算与交付契约 |
| Provider / 工具故障 | 明确错误码、超时或缺文件 | 单列基础设施可靠性修复 |

这些行动是结果解释模板，不是预先确定的结论。不能只展示胜出的演示案例。

## 12. 实施拆分与验收标准

| 阶段 | 范围 | 验收 |
| --- | --- | --- |
| P0 契约 | Task / Experiment / Run schema、策略定义、预算口径 | validate / plan 无模型调用；配置缺项立即失败 |
| P1 执行 | policy 注入、工具隔离、全局预算、最终提交、trace | fake 可精确复现四组；两种 MCP 路径行为一致 |
| P2 评分 | 8 个开发样本起步、隐藏检查、开放题锚点 | 同一交付重复评分一致；评分秘密对 Agent 不可读 |
| P3 Pilot | 64 runs、错误分析、冻结版本 | 报告包含四组、全部失败与用量覆盖，不输出“已证明” |
| P4 锁定评测 | 48 任务、576 runs、配对区间与转移表 | 可从记录重建主表；不挑样本、不动态改评分器 |
| P5 决策 | 必要计算量消融、人格/产品配置实验 | 输出任务级适用边界与证据不足项，再提路由改动 |

需要的工程测试围绕实验有效性，而不是验证某个策略一定获胜：

1. A / B / C 在进程内、子进程 MCP、原生工具路径均无法偷偷调用其他 Agent。
2. B 与 C 的阶段目的、工具权限、初始资料一致，仅执行身份按策略变化。
3. 所有动态受邀 / 恢复 / 失败 attempt 纳入统一预算；往返槽位预留正确。
4. 某 run 的消息、session 与产物不能泄漏到下一个 run；隐藏答案不可读。
5. 缺用量保留未知，累计与增量事件不重复计费。
6. completed 但无有效交付、超时、预算超限均判失败；报告分母保持完整。
7. 暂停恢复不重复记账；相同 manifest 与评分记录可以重建相同统计结果。

评测系统的完成标准是：**能可信地发现多 Agent 的收益和退化，并解释证据边界**。是否修改默认路由，等待实验结果决定。
