# Unity：三个值得重点讲的事故

整理日期：2026-10-26。面向 AI 应用、Agent 工程、后端和全栈岗位。案例来自项目已有事故记录与代码，不补造生产规模、用户增长、节省费用或成功率。

以下第一人称稿用于讲述项目经历。介绍个人贡献时，请区分自己提出的需求、参与的决策、亲自完成的实现/验证，以及 Codex 等协作者完成的部分；不要把项目成果统一表述成个人手写实现。已有升级记录明确披露了人类与 Codex 的分工。

## 面试开场：先让对方理解项目

> Unity 是我持续迭代的本地多 Agent 工作台，把 Codex、Claude Code、Antigravity 和文本 API 接到统一角色与任务系统。用户可以先聊天澄清，再确认任务提议，团队在独立工作区里持续推进。项目里我最关注三件事：真实 CLI 的运行边界、产物是否能可靠交付，以及模型、工具和宿主并发时的状态一致性。下面这三个事故，分别让我修正了验证方法、交付接口和状态机设计。

项目规模口径：本地单用户、持续自用；没有可引用的大规模生产用户或 QPS 数据。技术栈为 React/TypeScript、FastAPI、SQLite、本地 CLI 与 MCP。

| 案例 | 适合展示的能力 | 一句话结论 |
| --- | --- | --- |
| 1. 三种 CLI 在讨论沙箱中同时启动失败 | 系统集成、隔离边界、对照诊断、真实验收 | 协议替身通过不能证明真实 CLI 可用 |
| 2. HTML 已经存在，仍耗尽十分钟且没有正式回复 | 性能分析、接口设计、前后端交付语义 | 大文件用宿主导入，产物保存独立于发言完成 |
| 3. 结果先提交，宿主续租却报过期 | 并发与事务、状态机、确定性回归 | 已完成的同一执行凭证无需续租，终态不能被复活 |

推荐讲述顺序：AI/Agent 岗先讲 1，偏产品与全栈先讲 2，偏后端与基础设施先讲 3。每次选一个展开，其他两个留作追问。

## 案例一：演示能跑，三个真实 CLI 却全部启动失败

### 当时遇到什么问题

讨论 V2 为了让角色真正独立思考，引入冻结输入、提交屏障与受限进程。结果用户启动真实讨论时，Codex、Claude、Antigravity 都失败。界面只给出接近“未提交结果”的通用错误，用户看不出失败发生在初始化、认证还是模型阶段。

这是实现和交付验证遗漏。演示与替身检查覆盖了宿主协议，却没有覆盖三个真实 CLI 各自的初始化契约。单独运行 `--version`、`--help` 也无法证明隔离环境能完成任务。

### 如何定位

先区分逻辑回合与进程尝试：界面的 `3/13` 是阶段回合计数，实际上已经尝试六次，每个逻辑回合最多两次。继续扩大次数只会重复失败。

随后分别检查三个启动路径，保持目标能力与隔离要求不变：

| Provider | 被证据确认的问题 | 对应方案 |
| --- | --- | --- |
| Codex | 管理偏好初始化所需的只读系统资源被禁止，报 `Failed to synchronize managed preferences` | 精确允许必要的偏好和共享缓存读取 |
| Claude | 使用共享临时目录触发 `EPERM`，隔离环境还遗漏认证/本地模型代理连接字段 | 每轮独立临时目录，仅继承连接和模型环境配置、放行实际代理端口 |
| Antigravity | `-p` 后的参数被当成提示词；修正后暴露运行目录与 Keychain 依赖 | 使用 `-p=<prompt>`，独立 HOME/MCP/数据目录，以只读别名复用已有登录 |

Codex 使用无凭据的新目录作对照：沙箱外能够通过初始化，之后才因无凭据返回 401；沙箱内则停在偏好同步。清理父应用环境变量后仍能复现，因此不能将问题简单归因于继承了某个变量。

### 为什么选择这个方案

| 备选 | 取舍 |
| --- | --- |
| 整体关闭沙箱，先让 CLI 跑起来 | 会破坏冻结输入和讨论隔离要求，无法证明角色没有读取其他结果 |
| 复制用户全部 HOME 或全局配置 | 扩大读取范围，可能加载 hooks、旧会话与无关配置，也不利于复现 |
| 增加预算、重复创建讨论 | 初始化条件不变，不能解决参数、目录和权限错误 |
| 分 Provider 适配最小运行依赖 | 最终采用；共同协议保持统一，启动契约按实际 CLI 分别处理 |

同时补充安全错误分类、退出码与尝试数。私有诊断保留致命错误，公开错误不包含封存观点、原始正文和个人路径。

### 取得了什么成果

历史真实验收在临时数据库中使用实际执行器、路由和沙箱：三人独立提交，操作者明确选择综合者，另外两人复核，最终正常收束。无分歧与复核无发现分支共 **6 个回合、6 次有效提交、6 次尝试，零重试**。

CLI 修复阶段后端 705 项、前端 214 项通过，构建通过；后续 `/discuss` 交互阶段后端 774 项通过、1 项 opt-in 跳过，前端 228 项通过。这些是各阶段的历史记录，不能相加，也不代表本次文档修改执行了这些测试。

真实闭环验证的是本机安装版本、登录、连接、MCP 和阶段推进；没有证明复杂议题质量、所有故障分支或跨平台可用性。固定连通性题目不能作为“模型消除了讨好”或“多 Agent 更准确”的证据。

### 约两分钟口述稿

> 我在 Unity 里遇到过一次很典型的集成事故：讨论演示能跑，三个真实 CLI 一进入隔离环境却全部失败。最初界面只显示没有提交结果，几乎无法判断卡在哪层。
>
> 排查时先把逻辑回合和进程尝试分开，再分别对照三个 CLI 的启动链路。最后发现它们是三个不同的问题：Codex 需要读取系统偏好缓存，Claude 的临时目录和连接环境不完整，Antigravity 既有参数绑定问题，也依赖运行目录和 Keychain。
>
> 方案选择上，没有整体关闭沙箱，也没有复制整个用户目录，而是按 CLI 精确补齐最小运行依赖，同时保留冻结上下文和提交屏障。验证也从检查版本号升级成真实的读上下文、结构化提交、综合和复核闭环。
>
> 最终固定题目用六个回合、六次提交完成，零重试。这件事让我形成一个交付标准：统一协议可以用替身测试，但真实 CLI 的启动、认证与最终提交，必须单独提供真实证据。

### 容易被追问的点

- **为什么需要进程隔离，而不只写提示词？** 独立思考需要控制可读材料；提示词不能阻止模型读取数据库、文件或本地 HTTP。宿主协议与进程权限共同限制输入来源。
- **如何防止最小权限越修越宽？** 对必要资源做正向验收，同时测试其他临时目录、应用接口和未允许代理端口仍被拒绝；不把一次成功等同于边界全面正确。
- **为什么没有把真实验证放进所有默认 CI？** 依赖账号、机器权限和额度，适合作为明确启用的集成证据；默认离线检查保留可复现性，跳过真实验证时如实记录。
- **现在每次发版都会做完整真实闭环吗？** 当时记录只证明该次执行，持续的最小真实提交门禁仍有待落实，不能声称已经自动化覆盖所有发布。

证据：[STAR 原记录](../incidents/2026-10-20-deliberation-v2-startup-star.md)、[原始技术排查](../incidents/2026-10-19-deliberation-v2-cli-startup-failures.md)、[当前隔离适配器](../../backend/app/adapters/deliberation_cli.py)。

## 案例二：文件早已存在，模型却在交付时耗尽预算

### 当时遇到什么问题

用户请求查看一个 HTML demo。上一轮已经生成文件，下一轮却仍运行到 **600 秒硬截止**，没有调用 `publish_message`，用户只看到超时。不是完全没有结果：临近截止时文件已经通过 MCP 登记。

表面上像“模型太慢”，实际包含三个不同事实：大文件的交付方式昂贵、回合没有及时收口、产物展示依赖正式消息。Provider 期间还出现 503，不能把整段耗时都归给某个本地工具。

### 如何定位

按时间线对照任务事件、有界诊断、原生日志和文件字节差异：

- 58 次已完成原生工具调用，累计工具执行时间约 **2.554 秒**，最长约 0.518 秒。大部分墙钟时间发生在工具之间及模型/服务等待阶段；无法据此进一步精确拆出网络耗时。
- 本轮只有 3 次 Hub MCP 调用：`log_thought`、`read_artifact`、`write_artifact`，都成功；从未调用 `publish_message`。
- 当时 `write_artifact` 要求传全文。约 **35,000 字符**的现有 HTML 被再次经过模型输出，末次写入前生成约 **71.26 秒、12,748 output tokens**。
- 重输并没有形成新方案，还将一处头像/颜色字段改坏。最终文件登记时只剩约 27 秒，随后 503 和截止使正式发言未完成。

因此，不能简单说“58 个工具卡住了”，也不能把工具时长相加后声称已解释全部十分钟。

### 为什么选择这个方案

| 备选 | 取舍 |
| --- | --- |
| 再次提高超时 | 可以临时缓解，但仍然付出重复输出成本，也保留文件损坏风险 |
| 让模型输出更精简的 HTML | 会改变已有交付内容，不满足原文件展示与下载需求 |
| 将 CLI stdout 当成正式回复 | 破坏消息权威性，调试输出或错误也可能变成角色发言 |
| 宿主直接导入现有文件，文件卡独立展示 | 最终采用；保留原始字节，把保存与发言的状态分别记录 |

`write_artifact` 增加与 `content` 二选一的 `source_path`。宿主检查工作区边界、同会话产物归属、普通文件类型和大小，再直接导入字节。不能因为导入性能更好就允许模型读取任意本机路径。

前端从任务快照和 SSE 派生文件卡，文件登记后即能预览/下载。超时、后续任务和刷新都保留卡片，同时明确“已保存”不等于“已验证”或“已交付完成”。

### 取得了什么成果

历史浏览器验收确认：文件卡在运行中出现，HTML 可预览并交互；模拟超时、追加任务、刷新重开后保留，下载内容与源文件**字节一致**。无需重跑或修改历史任务，已有登记产物也能被展示。

后续实施记录为后端 832 项通过、1 项跳过，前端 234 项通过；补充 stdio 导入及卡片顺序后，受影响后端 145 项、前端 11 项通过，构建通过。

新接口从机制上移除了“已有文件必须由模型重输全文”的要求，但当时没有运行同任务的修复前后成本基准，不能声称实际节省了 12,748 tokens、固定提速比例或对应金额。也没有重新调用模型完成原来的新 demo 请求。

### 约两分钟口述稿

> 有次用户要看一个已经生成的 HTML demo，Agent 却又跑满十分钟，最后页面只显示超时。我把事件、工具时长和文件差异放到一起看，发现本地 58 次工具执行累计只有约两秒半，不能把问题归结成工具卡住。
>
> 一个关键成本在交付接口：当时写产物必须提交全文，所以三万五千字符的 HTML 又经过模型输出了一遍，单次生成就花了约七十一秒、一万两千多 output tokens，还把一个字段改坏了。文件最终已保存，但因为没有正式发言，用户不容易拿到结果。
>
> 最终把两个问题分别处理：宿主新增受路径和会话边界保护的文件导入；前端让文件卡独立于正式回复出现。验收检查了运行中展示、超时后保留、刷新和下载字节一致性。
>
> 这件事让我认识到，Agent 性能优化不只是换更快的模型，也要检查接口是否迫使模型重复搬运数据，以及状态展示有没有把可用成果藏起来。

### 容易被追问的点

- **为什么不直接发本地文件路径？** 路径不等于稳定交付版本，也未解决会话归属、下载与后续文件变动。导入形成宿主管理的产物记录。
- **怎么处理符号链接越界？** 实现先解析真实路径，再检查允许的工作区/产物来源；普通文件和大小检查另行约束。相关负向用例比只测成功导入更重要。
- **文件卡显示成功会不会误导用户？** 卡片只说明文件已登记，验证、正式回复和整项任务状态继续分别展示。
- **还能优化什么？** 剩余预算提示、重复探索检测、结构化 Provider 错误合并是当时建议；这次交付没有实现这些，不能算入成果。

## 案例三：提交已经成功，却被续租逻辑当成失败

### 当时遇到什么问题

对话式自主任务升级准备 PR 时，全量回归出现 **1011 通过、1 失败、1 跳过**。失败来自既有讨论隔离执行的长回合用例；单独重跑又能通过。

这不是已证实的大规模线上故障，而是交付阶段发现的并发缺陷。它的价值在于：对一个看似“偶发测试”的现象继续追到状态机根因，并将它转成不依赖时序运气的回归。

### 如何定位

适配器轮询 CLI 的同时，MCP 桥可以提交结构化结果。两条路径各自都正确，组合后存在“检查与使用之间状态改变”的窗口：

```text
适配器                         MCP 提交路径                 数据库
读到 lease=running  --------------------------------------> running
                               校验并提交结果 ------------> submitted
进入续租事务，再检查 lease -------------------------------> submitted
旧逻辑要求 running，于是报 lease expired
```

事务外刚读到 running，不能保证事务内仍为 running。提交是正常的前进，旧代码却把“已经完成、不需续租”与“无效凭证/过期执行”混为一类。

### 为什么选择这个方案

| 备选 | 问题 |
| --- | --- |
| 重跑测试，归类为 flaky | 没有修复真实窗口，模型速度或机器负载变化后仍可能出现 |
| 捕获并忽略所有 lease 异常 | 会同时吞掉错误角色、错误 Provider、旧 token 与真正失效状态 |
| 把 submitted 改回 running 再续期 | 复活终态，可能允许迟到工具继续写入 |
| 在续租事务中识别同一凭证已提交 | 最终采用；仅对确切成功情形返回“不需要续租”，其余仍严格拒绝 |

修复位于 `renew_turn_lease` 的事务内部：核对讨论未结束、状态为 submitted、角色一致、Provider 一致、token 恒定时间比较一致后，返回 `False`。不修改状态、不延长过期时间。正常 running 返回 `True`；适配器仅在确实续租时写延长事件。

这是一项明确的 API 语义：`False` 表示同一执行已完成，无需续租；异常表示不合法。不是一概将失败当成成功。

### 取得了什么成果

增加确定性回归：先让提交成功，再调用续租，断言返回 `False` 且整个状态保持不变；再分别换错角色、Provider、token，断言仍被拒绝。保留原有真实子进程隔离用例。

修复已随对话式自主任务升级进入当前代码基线。成果是消除了这一已知提交/续租窗口的错误判定，并建立可重复的状态与权限回归；原记录没有提供修复后的线上事故率或延迟变化，不补造这些数据。

### 约两分钟口述稿

> 升级准备 PR 时，全量测试出现一个很有价值的偶发失败：一千多项里只有一个长回合隔离用例报 lease expired，但单独重跑能过。我没有把重跑通过当成解决，而是继续检查提交与续租的并发关系。
>
> 原因是适配器先读到执行状态为 running，准备续租；这时另一条 MCP 路径已经提交成功，把状态改成 submitted。等续租进入事务再校验，旧逻辑只接受 running，于是把正常完成误判为过期。
>
> 修复没有吞掉所有异常，也没有复活已完成状态，而是在事务里核对同一角色、Provider 和 token 确实已经提交时，返回不需要续租；其他错误仍然拒绝。然后用确定性测试先提交、再续租，检查状态完全不变，并覆盖错误身份。
>
> 这个问题说明，Agent 宿主也是并发系统。数据库有事务，不代表事务外的检查就安全；必须为每一种状态前进定义清楚的结果。

### 容易被追问的点

- **SQLite 单写者为什么还有竞态？** 两个写事务可以顺序执行，但前面的读发生在续租写事务之外；串行写并不让整段“读—等待—再写”自动原子化。
- **为什么不是全局加锁？** 关键判定可以在已有持久事务中完成；进程内锁无法替代数据库状态和跨重启身份检查，还会扩大临界区。
- **幂等和续租是什么关系？** 幂等防止同一逻辑操作重试产生重复效果；续租延长仍在执行的授权。已经提交的同一授权不需要延长，两者不能混同。
- **为什么不直接做 exactly-once？** 数据库内可以事务化去重，文件和外部发布不能随 SQLite 回滚。项目对未知副作用先核对，不能承诺跨所有外部系统 exactly-once。
- **普通聊天超时也被这个修复解决了吗？** 没有。这是讨论执行 lease 的已知竞态，不等于普通回合总预算、休眠时钟或持续工作入口已全部解决。

## 三个案例共同形成的工程方法

先用数据库事件、实际 CLI 诊断和文件事实还原过程；明确模型推理、工具执行、结构化提交、任务完成与上线验证分别意味着什么；选择能保留边界的最小修复；用对应层级的真实闭环或确定性回归验证。

不要将历史 600 秒截止称为当前默认配置，也不要把一次真实连通性测试说成完整开发成功。项目存在多轮演进，每个数字都必须带上发生阶段。
