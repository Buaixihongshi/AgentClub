# 我为什么做 Unity：让几个 AI 伙伴把一件事接着做完

> 摘要：Unity 是一个本地多 Agent 工作台，把 Codex CLI、Claude Code、Antigravity 和文本 API 接到统一的角色、会话与任务系统。这个项目真正花时间的地方，是让协作有来源、让工作能接续、让交付有证据。
>
> 文中能力对应截至 2026-10-26 的代码，事故数字来自当时记录。项目由我持续推动，并与 Codex 等 AI 助手协作开发与验证。

## 起点是一个很简单的愿望

我想有一个可以长期待着的 AI 工作群。

遇到一个想法，可以先找伙伴聊清楚；需要不同视角时，让他们分别想一想；决定做了，就有人负责推进。下一次回来，不必把上次说过的需求重新解释一遍，也不用在几个终端之间手动搬运上下文。

角色选择了张楚岚、冯宝宝和王也。人物的性格让交流更有辨识度，但我不希望角色被固定成某个岗位。提出问题、写代码、做检查，都应该取决于当前任务，而不是名字。

这个想法逐渐变成了 Unity：一个运行在本机的单用户工作台。前端用 React 和 TypeScript，后端用 FastAPI 与 SQLite，底层连接现有 AI CLI 和模型 API。

做下去才发现，把几个模型放到同一个界面里，只完成了很小的一部分。

## 角色可以稳定，模型可以替换

我把角色、模型连接和路由分别管理。

角色保存人格、会话身份与记忆；连接决定使用哪个 CLI 或 API；路由决定主用、备用以及具体模型。今天王也由 Antigravity 执行，明天改用另一个连接，用户仍然是在和同一个伙伴继续工作。

这种分离也让接入过程更平缓。没有账号时，先用内置演示模式体验会话；配置好一个 CLI，就可以先让三位伙伴共用它；之后再按需要分配不同模型。

不过，连接能力并不完全相同。文本 API 可以分析和参与结构化讨论，CLI 才能进入受限开发执行路径。界面上的“可以选中”，不应该让用户误以为它们拥有完全相同的工具能力。

## 从聊天走到持续工作，需要一份可以确认的约定

早期做法更接近聊天接力：一个角色说完，交给下一个，最后给出总结。

真正拿它迭代项目时，问题很快出现。一次回复结束之后，谁继续？改过的文件有没有验证？用户后来补充的条件有没有进入任务？浏览器关掉，工作是不是也结束了？

现在的入口仍然是聊天。用户先 `@` 一位伙伴表达目标，角色在需要持续推进时整理任务提议，写清目标、范围、负责人、验收条件和交付终点。用户查看并确认后，后端才建立可调度工作。

对话页保留交流，任务页追踪责任、决定和交付。负责人可以自己做完简单工作，也可以邀请其他角色协作；涉及数据、权限、协议等规定风险时，需要非作者审核。子任务做完，根负责人还要对原始目标负责。

新任务确认后有独立分支和代码目录。不同任务的代码相互隔离，当前执行依然保守串行。关闭页面不会清除已授权工作；恢复服务时先检查旧进程和文件变化，再决定如何继续。

这里最重要的设计是：整项工作的状态有独立的持久记录，一次模型调用只是其中一个动作。

## 三次故障，把项目推向了更具体的工程问题

### 演示通过，真实 CLI 全部失败

讨论功能升级后，我希望角色先独立思考，再交流分歧，所以加入了冻结输入和隔离执行。演示能跑，三个真实 CLI 却都启动失败。

排查发现，它们各有不同的运行依赖：Codex 需要读取系统偏好资源，Claude 的临时目录和连接配置不完整，Antigravity 则有参数绑定、运行目录和 Keychain 问题。

最终选择按 Provider 补齐最小依赖，保留隔离边界，再用实际 CLI 跑读上下文、提交、综合和复核。固定连通性题目完成了六个回合、六次提交，零重试。

这次故障让我重新理解“验收通过”的含义。替身可以验证协议，版本号可以证明命令存在；真实初始化和最终提交仍需单独验证。六次成功也只说明那条链路当时可用，不能证明多 Agent 在所有问题上都更好。

### 文件已经写好，用户仍然只看见超时

另一次，用户想看 HTML demo。文件已经存在，Agent 还是跑满十分钟，没有发出正式回复。

时间线里有 58 次完成的原生工具调用，工具执行累计约两秒半。一个明显的交付成本藏在接口里：当时登记文件必须提交全文，三万多字符的 HTML 又经过模型输出了一遍，单次生成约七十一秒、一万两千多 output tokens，还改坏了一个字段。

后续加入了宿主文件导入：模型只提供允许范围内的路径，由宿主保存原始字节。文件卡也独立于正式发言展示。即使这轮超时，已经登记的文件仍然可以预览和下载。

这次改动没有可引用的整体提速比例，但它移除了一个明确的浪费来源，也修正了用户拿不到已有成果的问题。文件保存、验证通过、任务完成，需要分别表达。

### 提交成功之后，续租却报过期

还有一个缺陷是在交付前回归中发现的。全量测试有一项偶发失败，单独重跑又能通过。

适配器读到执行状态为 running，准备续租；另一条 MCP 路径已经提交结果，将状态改为 submitted。续租进入事务后还要求 running，于是把正常完成误判为过期。

修复是在事务内核对同一角色、Provider 和执行凭证是否已提交：如果是，就返回不需要续租，保持终态；错误身份与失效凭证继续拒绝。回归测试先完成提交，再调用续租，明确检查状态不被改变。

模型系统里同样存在普通并发系统的问题。事务、幂等、进程归属和状态机，没有哪一项会因为接入了大模型就变得可有可无。

## 记忆要能看见，也要能改掉

持续协作还需要解决另一件事：哪些内容应该留到下一次？

Unity 目前按角色保存长期 Markdown 记忆，会话中保存滚动检查点，SQLite 为记忆维护可重建索引。普通任务、讨论和自主工作复用统一的上下文装配。切换模型时附上显式交接，避免执行模型变化后把已确认事实重置。

用户可以在设置里查看和修订记忆，也可以忘记、恢复或永久清除。忘记是从后续上下文移除，清除才是删除文件。

这一版没有向量检索，也不会自动让模型总结所有历史。我更希望先把事实归属、修订和遗忘做清楚，让“它记住了什么”成为用户能检查的内容。

## 比“说完成了”更重要的，是能找到依据

项目把 CLI 活动、MCP 调用、角色协作和产物归到回合中，在设置的观测页查看。用户可以从总览下钻到某一轮，知道实际使用了谁、发生过什么、哪里失败了。

成本有报价就用报价，没有就显示估算或未知；检查缺少证据时显示 `n/a`。现有规则只能找出部分声明与事件的矛盾，不能替代语义审核。

同样，我加入了单 Agent、自我反思、固定团队和动态 A2A 的对照运行器，把任务、角色与 Provider 的差异尽量拆开。目前的价值是提供可复现的评测方法，项目还没有足够证据宣称团队模式普遍更准、更快或更省。

开发环境和发布也采用类似原则：功能候选、主线 alpha、日常实例分别记录；用准确源码身份识别运行版本，发布前保留状态与前版。一次合并不代表服务已经升级，一条发布命令成功也不代表实际版本核对已经通过。

## 现在可以怎样使用它

你可以先用演示模式了解工作台，再接入自己的 CLI 或文本 API。想比较方案时输入 `/discuss`；希望持续开发时，让伙伴先提出任务提议，确认范围和验收条件。任务页面可以查看交付物、工作区，以及受管预览。

当前它仍然是本地单用户项目。真实 CLI 的讨论隔离和自主开发首版依赖 macOS；任务执行仍串行，还没有自动冲突合并和任意仓库选择界面。真实模型请求会将上下文发送给所选服务，Local-first 描述的是应用状态的存放方式。

对我来说，这个项目最有吸引力的部分，是每次自己使用时都能碰到一个足够具体的问题，再把它落实成接口、状态和可检查的结果。现在我最常用来检验 Unity 的问题也变得很朴素：回来之后，我能不能看清上次做到哪、已有的东西在哪里、下一步还需要谁来决定。

## 跨平台短稿：社区、公众号导语或项目动态

**标题：我做了一个本地 AI 工作群，让几个 Agent 能把工作接下去**

最近持续迭代的项目叫 Unity。它把 Codex CLI、Claude Code、Antigravity 和文本 API 放进同一个工作台，用张楚岚、冯宝宝、王也作为三位交流伙伴。角色身份、执行模型和路由分别配置，可以换模型、保留上下文。

我想解决的场景是：先把一个想法聊清楚，再让团队在明确范围内持续推进。用户在聊天里确认任务提议，任务页追踪负责人、验收、决定和交付物；新任务拥有独立代码目录，已授权工作不会因为关掉页面就消失。

开发过程中，最有收获的反而是几次故障：演示通过却三个真实 CLI 都无法在沙箱启动；现成 HTML 因为被模型重新输出而耗尽预算；结果已提交却被续租逻辑误判失败。它们分别推动了真实 CLI 验收、宿主文件导入和事务内状态检查。

现在项目还支持 `/discuss` 结构化讨论、可管理的长期记忆与模型交接、文件预览、回合观测和对照评测。它仍是本地单用户项目，当前任务串行执行，部分真实执行能力依赖 macOS。

项目由我持续推动，与 Codex 等 AI 助手协作开发。源码与文档：[Unity](https://github.com/Buaixihongshi/Unity)。欢迎交流你在长期 Agent 任务、交付证据和失败恢复中遇到的问题。
