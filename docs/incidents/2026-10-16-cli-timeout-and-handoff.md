## 1. 根因分类

### E：隐含假设——把认证探测失败当成最终状态

`read_agy_log_hint` 只要看到 `not logged into Antigravity` 就报告未认证。实际两份日志 `cli-20261016_115018.log`、`cli-20261016_120200.log` 均在早期探测失败之后出现 keyring / OAuth 认证成功，之后才发生内部超时。原提示导致聊天中的诊断错误地引导用户重新登录。

同时，适配器只识别旧版 stdout 的 `timed out waiting for response`，未识别新版 stderr 的 `print timeout after ...`，把内部超时归为没有调用 `publish_message`。

### C：变更传播遗漏——默认值不是实际生效值

任务 25 修改了代码默认超时为 300 秒，但 `data/hub_settings.json` 中用户设置仍为 240 秒，优先级更高。现有运行进程也没有自动重载 Python 代码。反复创建新任务不会续跑已经被终止的进程。

### B / D：跨层契约和测试缺口——交接引用缺少来源

`conversation-trace-spec.md` 存在于任务 `m_62915114f1c74b7da2968cc779deb26b`，大小为 10492 字节。调用方只传文件名，旧接口和产物索引都以当前任务为范围，因此报不存在。

任务 25 在终止前新增了部分 `source_mission_id` 支持，但没有补全产物发现链路；初始边界检查还允许无会话 ID 的任务绕过跨会话限制。修复必须覆盖“产物索引 → prompt → MCP schema / handler → tools → 文件系统”。

产物读取失败是已证实的交接问题，但现有证据不足以证明它是 Claude 所有超时的唯一原因。

### A / D：诊断缺失

只有显式设置 `YIREN_MCP_DEBUG_DIR` 才会保存 CLI 输出，事故进程未配置。数据库记录了 MCP 行为，却没有 Claude 后续原生操作的完整证据。仅增加超时时间不能保证复杂任务都完成。

## 2. 为什么此前未恢复

1. 认证错误提示遮蔽了后续认证成功事实，导致排查方向偏离真实超时。
2. 多次“人呢 / 继续”创建了新任务，没有恢复旧进程，并再次丢失 spec 的任务归属。
3. 改默认值没有覆盖已有用户配置；修改代码没有经测试和重启形成闭环。
4. 负责修改的 Claude 自己被 240 秒上限终止，留下半完成的实现，不能将聊天中的承诺当成部署成功。

## 4. 系统性检查与后续边界

- 认证故障、CLI 内部超时、宿主硬超时、缺少 MCP 发言是不同原因，错误文案和日志应分别表示。
- 工作树修复、运行目录文件、已加载进程、用户配置是四个不同状态，验收必须核对实际运行服务。
- MCP 是 agent 到宿主的唯一协议；没有从 stdout 生成聊天消息，没有按 agent 正文中的 @ 自动路由。
- 保留历史 blocked 记录；不自动重试那些可能已经产生部分代码修改的任务，避免重复执行副作用。
- 本次未增加 provider 自动兜底。5 分钟是单次调用预算，不保证任意实现工作都能在一轮内完成。
- 后续若仍超时，可用新诊断定位最后输出和退出阶段；历史 Claude 阻塞点无法事后补造。
