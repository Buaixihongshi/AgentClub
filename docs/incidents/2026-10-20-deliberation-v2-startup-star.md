# 讨论 V2 启动失败事故复盘（STAR）

事故发生：2026-10-19；修复与复盘：2026-10-20。文中时间均为北京时间（UTC+8）。

事故状态：已完成本地修复及真实 CLI 连通性验收。相关实现包含在 [PR #18](https://github.com/Buaixihongshi/AgentClub/pull/18) 中；本复盘作为独立文档提交，不代表该实现已经合并或获准发布。

## S — Situation：背景与影响

讨论 V2 从顺序发言改为独立判断、分歧讨论、人工选择综合者、综合、原参与者复核和收束，目的是减少首位发言对其他参与者的锚定。为保证首轮独立性，新适配器采用 macOS 沙箱、独立工作目录和宿主 MCP 桥。

离线协议、沙箱中的 CLI 替身和浏览器演示验证通过后，首次真实三人讨论在独立思考阶段失败。用户看到“Provider 运行失败、超时或结构化提交无效”和“重试额度已用尽”，无法判断具体原因。

| 证据 | 观察结果 |
| --- | --- |
| 议题 | “如何设计咱们的 eval” |
| 时间 | 2026-10-19 23:22:10 开始，第二次尝试于 23:22:16 结束 |
| 协议 / 规则 / 构建 | `deliberation_v2` / `deliberation-v2.2` / `69419869aa5c6246` |
| 执行状态 | 三位参与者均失败，每位尝试两次；状态为 `blocked`，仍在 `independent` 阶段 |
| 工具访问 | 三位参与者的 `context_read` 均为 `false`，没有有效观点提交 |
| 单次耗时 | 六次进程耗时为 206～809 毫秒，未达到执行超时 |

直接影响是该场讨论无法开始，六次启动尝试全部失败。没有证据表明这是模型推理质量问题、总讨论预算耗尽或结构化内容校验失败；失败发生在调用讨论工具之前。没有有效提交需要解封，排查与修复也未改写原失败任务或自动重跑用户议题。

无法据此量化其他任务的影响、经济损失或持续故障时长；本复盘不将缺少证据的范围计入事故结论。

## T — Task：恢复目标与验收责任

恢复目标是让当前配置中的 Codex、Claude 和 Antigravity 都能完成真实初始化、读取冻结上下文并提交有效结果，同时保留原有隔离边界、人工决策、有限重试和历史记录。

验收需要同时回答三个问题：

1. 每种真实 CLI 的参数、临时目录、认证和连接配置是否可用，而不只是二进制能够运行 `--version` 或 `--help`？
2. 模型是否通过 MCP 完成了正式提交，而不只是退出码为零或 stdout 有内容？
3. 用户是否能够区分启动错误、认证错误、超时和提交缺失，且不会看到未解封正文或凭据？

项目维护者提出需求、报告失败并确认后续技能入口；Codex 负责本次实现、排查、修复、测试与记录。是否合并和发布由仓库所有者审批，测试通过不能替代审批。

## A — Action：定位、修复与验证

### 1. 用实际回合证据定位失败层级

先只读核对任务事件、每次 Provider 的退出码、租约状态及私有诊断，再结合真实 CLI 的最小初始化对照复现。没有通过重置次数或反复新建用户讨论来定位问题。

| Provider | 确认的原因 | 修复措施 |
| --- | --- | --- |
| Codex | 沙箱内创建会话前报 `Failed to synchronize managed preferences`；原诊断只留下了次级网络策略警告 | 放行 Codex 管理偏好所需的只读偏好访问和 macOS `apple.cfprefs.` 共享缓存读取，保留用户目录与本地应用接口限制 |
| Claude | CLI 使用共享临时目录，报 `EPERM`；进一步真实验证发现用户设置中的认证及本地模型代理配置也被隔离启动配置遗漏 | 将 CLI 临时目录与缓存置于本回合目录；仅继承连接和模型环境字段，并仅放行实际模型代理端口；保留认证，不加载用户 hooks 或旧会话 |
| Antigravity | `-p` 后追加的 `--new-project` 被当作提示词；修正后又暴露运行数据目录与 Keychain 依赖 | 使用 `-p=<prompt>` 显式绑定提示词；使用独立 HOME、MCP 和数据目录，通过现有登录 Keychain 的只读文件别名维持认证，不修改全局 MCP 配置 |

Codex 初始化对照使用全新、无凭据的目录，沙箱外可以通过该初始化步骤，随后因无凭据返回 401；清理继承的 `CODEX_*` 环境变量后，沙箱内仍能复现管理偏好错误。这排除了“父应用环境变量就是直接原因”的简单解释。该对照没有成功进行付费生成。

### 2. 补全不泄露封存内容的诊断

- 区分并保存失败类别、Provider、退出码和尝试次数；公开视图使用预定义的脱敏提示。
- 私有错误保留致命错误所在的末尾，避免截断后只剩次级警告；不将原始 CLI 正文作为用户诊断展示。
- 明确 `3/13` 是阶段回合计数，实际已有六次进程尝试。每回合最多两次，因此重试耗尽不等于总讨论预算用尽。
- 保留已接受结果与原任务状态，不伪造交付、不自动放大重试预算，也不通过整体关闭沙箱恢复运行。

### 3. 分层验证恢复结果

先补参数绑定、临时目录、认证环境、诊断与隔离边界的回归，再验证三个真实 Provider 分别完成 `read_context` → `submit_discussion_result`。

随后在临时数据库中，用实际生产执行器、提示词构造、ProviderRouter 和沙箱运行固定连通性题目“先验证”：三人独立提交，验收操作者明确选择冯宝宝综合，楚岚与王也复核，最后正常收束。无实质分歧、复核无发现时，流程跳过讨论轮并复用综合稿，共六个回合、六次尝试，没有重试。验收任务没有写入用户实际数据库。

### 4. 后续交互调整保留执行约束

用户随后要求将讨论封装为项目技能，并明确选择聊天命令 `/discuss 议题`。主聊天移除了模式切换、角色选项和六阶段大板；后台继续执行冻结输入、阶段屏障和复核，必要时才提示选择综合者、处理价值取舍或运行失败。此项是事故后的产品调整，不是三个 CLI 启动失败的直接修复。

独立检查同时纠正了精简界面带来的四类回归：用户决定需要持久化聊天确认；最终结果需要保留可展开的依据和复核处置；历史与侧栏预览需要过滤中间正文；旧 V1 幂等请求需要兼容历史默认字段。普通聊天和旧 API 保持兼容。

## 根因与防复发

直接技术原因是三个真实 CLI 的初始化契约与新隔离适配器不一致。促成因素是：测试替身验证了统一协议，却未覆盖每种真实 CLI 的启动路径；`--version`、`--help` 和演示 UI 通过，被当成了接近可用的证据。统一错误提示又掩盖了启动层差异，导致用户无法从界面判断原因。

这是实现与交付验证遗漏，不能归因于模型不配合或用户重试方式不当。

| 措施 | 状态 | 可检查的完成条件 |
| --- | --- | --- |
| 为各 CLI 分别检查参数与运行目录，覆盖代理端口允许及其他本地端口拒绝 | 已加入回归 | 对应正向和反向用例通过，不能只用一种 CLI 替身代替全部参数路径 |
| 记录安全错误类别及退出码，保留致命诊断 | 已实现 | 启动、认证、超时和未提交可区分，测试确认封存正文与私密路径不会进入公开错误 |
| 安装版 CLI 初始化检查保持显式 opt-in | 已实现 | 使用无凭据目录完成初始化探针，不能将“默认跳过”写成真实 CLI 已验收 |
| 为 Provider 版本变更或隔离配置变更执行最小真实提交与闭环验收 | 本次已执行；持续发布门禁待落实 | PR 中记录安装版本、目标 head、实际提交结果和测试范围；需要真实调用时明确控制成本 |
| 将连通性验证与讨论质量评估分开 | 边界已明确；质量评估待完成 | 用真实项目议题、证据引用及少数观点保留情况评估，不能用一致意见或多数票判断可靠性 |

后续变更的实现者负责补齐相应验收证据，仓库所有者审核当前 head；上表“待落实”项没有被本次文档修改自动完成。
