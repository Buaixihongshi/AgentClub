# 对话式自主任务升级复盘

日期：2026-10-24（Asia/Shanghai）。范围：从共享开发约定、自适应调度，到对话式任务提议、任务双视图及对应环境配置修复。

## 目标与最终行为

用户希望在 AgentClub 中直接 `@` 一位伙伴提出需求，先通过对话澄清；需要持续工作时，由角色整理可确认的任务提议。用户确认后，团队在授权范围内按需调查、设计、实现、验证或协作。关闭聊天页面不丢失工作；关键选择、审核和上线批准可以追溯到具体需求与交付版本。

这里的自主性指负责人在目标与边界内选择必要动作，不是固定执行“张楚岚 → 王也设计 → 宝宝开发 → 王也审核”。没有 UI 的工作可以跳过设计，简单工作可以一位角色完成。规定风险需要非作者审核；模型不能给自己扩大授权，也不能以聊天中的“完成”代替证据。

用户在本次会话明确表示 5180 的功能改动已验证完成。该事实记录为**开发候选体验确认**，不替代后续 PR 当前 head 的 Owner approval、合入主线后的 alpha 验收或日常部署批准。

## 问题表现与根因

| 表现 | 根因 | 对应处理 |
| --- | --- | --- |
| 交流结束后不清楚谁继续、还缺什么 | 聊天记录承载了执行状态，一次 mission 结束与整项需求完成混用 | 共享任务持久保存负责人、约定、检查点、依赖、决定、证据和累计预算 |
| 看似需要每个任务都走设计、开发、审核的固定顺序 | 用示例角色顺序代替了实际验收缺口 | 负责人选择必要动作；调度器检查条件并落实分工，简单任务保留短路径 |
| 改过代码后仍可能引用旧审核 | Git HEAD 无法区分同一提交下的未提交内容；结论缺少准确版本边界 | 保存文件内容快照，验证、审核和上线批准关联约定版本与候选 ID |
| 共享任务栏占据大量聊天空间，路径、历史和技术标识没有重点 | 将任务全部状态与原始记录平铺进对话 | 对话／任务双视图；聊天保留紧凑待办；默认六项重点记录，完整记录和来源按需展开 |
| 新建与已有会话呈现两套外观，第一次改色仍不像原设计 | 为局部任务 UI 引入了独立应用壳、蓝色强调、冷灰色覆盖与不同字体字重 | 最终按用户图 1 复用原 MissionHeader、侧栏、暖白／鼠尾草绿／深灰变量、点阵背景、描边与硬阴影 |
| 需求输入变成选择交付类型和填写任务表 | 把后台工作契约直接变成用户的前置操作 | 默认聊天；角色提出结构化提议，用户在对话中查看并确认；任务首页展示进度，不承担需求录入 |
| 提议可能与后来补充的需求不一致 | 只有“有一份提议”，没有记录其来源上下文 | 提议记录来源消息 ID、mission、角色回合和摘要；新增用户消息或替代提议使旧提议不能继续接受 |
| 曾把开发候选测试称作 alpha 验收，且测试角色全用 Codex | 未区分代码所在环境；旧启动器强制 alpha 演示，另有验证时手动简化路由 | 分开记录开发候选、主线 alpha 与日常；alpha 启动继承日常有效 CLI 路由、模型、备用配置与超时，数据独立 |
| 暂停、恢复、失败和重启容易变成重复执行或无限返工 | 依赖一次唤醒或内存状态，没有持久执行归属与有界恢复 | 原子领取、revision 检查、operation_id 幂等、累计预算、旧进程检查与只读恢复核对 |

## 经过与采用方案

1. **先定义可追溯的开发约定。** 保存原始来源、目标、范围、交付终点、验收项及验证方式。真实授权来自用户，角色可细化验收，但实质范围变化必须得到决定。
2. **建立共享任务与宿主执行边界。** SQLite 保存工作事实；后台检查循环在条件满足时原子领取一轮动作。角色负责业务判断，宿主负责状态、权限、验证和恢复。共用工作树串行执行，子任务不解除父责任。
3. **将固定流水线收敛为按需动作。** `invoke_agent` 是唯一实际协作入口；正文点名不能代替交接。独立审核按风险或明确要求加入。文档、开发、上线申请三种终点的权限分别限定。
4. **保留真实版本与证据。** 保存已跟踪文件、未忽略新增文件及未提交内容；审核必须覆盖当前约定与候选。发布必须绑定候选和目标环境，结果未知时只查询实际状态，不盲目重放。
5. **修正环境与真实 CLI 验证。** 配套修复见 [alpha CLI 复盘](2026-10-24-alpha-cli-parity.md)。配置继承只选取 CLI 字段，不复制日常聊天、数据库或 API 密钥文件；配置缺失或路由无法继承时明确报错，不静默换模型。
6. **整理任务 UI 与对话入口。** 采用用户选择的对话／任务双视图，再按用户最新图 1 统一完整视觉语言。预览仅打开时加载；历史记录、长路径和技术依据收进详情，草稿在视图切换时保留。
7. **补齐对话到持续工作的连接。** 普通对话中 `propose_work` 只保存提议，尚不创建可执行任务。用户接受具体提议后，才建立工作和授权；继续讨论则不启动。默认提议只交文档，明确开发范围才请求开发。
8. **用户确认开发候选，整理 PR。** 准备 PR 时发现独立头像测试改动；用户明确表示不用保留，遂只撤销头像相关源码、测试与演示文件，不清理业务记录。PR 在独立工作树整理，不提交本地示例、数据库、私有截图、配置或备份。

## 为什么采用这套方案

| 备选方案 | 本次取舍与原因 |
| --- | --- |
| 只靠聊天历史或每轮总结接续 | 不采用。不能可靠承担领取、幂等、依赖、恢复和准确审批；聊天保留讨论，执行事实入库 |
| 固定绑定三个角色及必经阶段 | 不采用为默认。无 UI 和简单任务会被迫增加步骤；用户可以为某个任务明确指定分工 |
| 再增加一个常驻大模型总调度员 | 本轮不采用。当前需求可由负责人判断加宿主规则完成；额外模型会增加成本和新的状态一致性问题 |
| 在共享工作树直接并行改文件 | 本轮不采用。尚无独立分支合并与冲突处理机制，先以串行保证可追踪和可恢复；将来可在任务独立工作树后扩展 |
| 用完整任务表单作为默认入口 | 不采用。用户希望自然表达需求，结构化约定应由角色整理；保留已有 API 兼容性与高级控制 |
| 根据“开始吧”等自由文本直接推断任意开发或上线授权 | 不采用。先确认可检查的提议；设计、开发、上线范围不能混同。既有明确单卡决定回复仍按原有规则处理 |
| 只记录 commit SHA，不封存实际文件 | 不采用。开发候选可能尚未提交，审核必须对应真实内容；使用内容寻址快照并关联证据 |
| 浏览器页面轮询驱动执行 | 不采用。页面关闭会中断工作；执行由后端持久调度，页面轮询只负责展示 |
| 引入第二套 UI 框架或整套复制 Clowder | 不采用。当前 React、Lucide、Markdown 与原生 dialog 已足够；组件源码保留在仓库，统一使用原设计变量，package.json 与 lockfile 不变 |

Clowder 的参考价值在于持久协作、聊天 `@` 路由以及长期任务的独立追踪，不在于复制其角色、品牌或依赖。其 [ChatInput](https://github.com/zts212653/clowder-ai/blob/main/packages/web/src/components/ChatInput.tsx) 承担消息输入，[TaskBoardPanel](https://github.com/zts212653/clowder-ai/blob/main/packages/web/src/components/TaskBoardPanel.tsx) 追踪持续事项，也保留可选手动建任务。AgentClub 的提议确认、预算和执行边界是本项目的选择。

## 最终效果与证据边界

- 用户可先 `@` 伙伴对齐需求，确认提议后持续推进；任务页用于识别负责人、进展、等待对象、关键决定和交付物。
- 记录保留人物、时间、来源回合、约定及交付版本；页面关闭和服务恢复不把任务事实丢回聊天记忆。
- 对话页不再被完整过程占满，采用原设计风格，桌面和 390px Chromium 的输入及主动作可达。
- 已有自动化验证并发领取、幂等、过期版本、恢复、预算、角色权限和决定卡；真实模型验证与替身验证分开记录。
- 5180 候选的用户体验确认已完成；准备 PR 不等于已经完成当前 head 的独立审查、alpha 验收或正式发布。最终检查和剩余事项见 [本次验收记录](../acceptance/2026-10-24-conversation-first-autonomy.md)。

## 当前限制与后续安排

当前是本地单用户、单共享工作树的串行调度；能力匹配仍主要依赖负责人选择，未实现自动挑选最优角色或默认固定团队顺序。受管执行首版依赖 macOS 隔离能力；不支持的平台与纯文本 API 会明确阻塞，不降级为仅靠提示词限制。完整物理手机、Safari、软键盘和生产部署未在本轮验证。

后续顺序：当前 PR 的检查与非作者审查 → 所有者针对准确 head 放行 → 合入 main → alpha 在准确主线提交上核对且沿用日常有效 CLI 配置 → 单独批准发布。回退应保留业务状态备份并使用既有发布恢复入口，不删除任务库来伪装恢复成功。
